## 1. 问题定义

### 1.1 场景

航空备件供应商收到航空公司或维修厂的询价（RFQ），通常要求 1–2 个工作日内回一张带价格的报价单。同一批客户，前后两封邮件的格式可以完全不同：正文 HTML 表格、正文制表符、Excel 附件、PDF 表单。一封询价可能是 7 行，也可能是 122 行。

业务员实际要做四件事：

1. **把行项目抠出来**——列名不统一（Part Number / 料号，Qty / 数量），优先级、交期、件状有的在表里，有的只写在正文。
2. **判断件状能不能接受**——客户要 FN（全新件）、SV（可服务件）、OH（大修件），供应商现货可能是另一种。这是商业判断，不是查表。
3. **找价格依据**——内部成本表给成本，价格资源表给供应商报价。缺一边不能凭感觉加价；两边都没有就必须转人工询价。
4. **按客户模板出单**——金额、大写、有效期、每行的件状 / 证书 / 交期，缺一项客户就退回。

### 1.2 三处不可控（这是真正的问题）

| 不可控 | 事实 |
|---|---|
| **格式不可控** | 官方六封邮件用了四种载体：正文 HTML 表格（A、D）、Excel 附件（B、E）、PDF 表单（C、F）、正文制表符（D 的 `text/plain`）。每封都要人眼重新对齐列名，最长的单 122 行。 |
| **依据不可控** | 报价单发出去，三天后客户问"这行为什么这个价"，答不上来。300 行官方素材里，只有 128 行能在两张参考表中找到价格依据，其余 172 行本来就没有。 |
| **判断混在计算里** | MOQ 超采、件状放宽、无价格依据，是三个性质完全不同的决策，在 Excel 里被压成同一个动作：「填个数字」。 |

### 1.3 现成做法为什么不够

- **纯手工 Excel**：122 行对齐一次 1–2 小时，错行的代价是报错价；官方模板只有 5 个固定明细行，21 行 / 122 行都必须动态增行。
- **纯大模型方案**：能读懂邮件，但会给出"看起来合理"的价格，无法回溯到单元格，也无法回答"这行为什么停住"。
- **纯规则脚本**：格式一变就崩，遇到客户用散文写的条款（C/F 各 3 条）读不出来。

### 1.4 目标（可验收）

1. 六封官方邮件（300 行）端到端跑通，行为一致；
2. 每一行都能回溯到「邮件 → 附件 → 表/页 → 行 → 列 → 原值」；
3. 没有价格依据时**不给数字**，而不是给一个估算；
4. 输出是客户模板的 DOCX 草案，不是自制的漂亮表格；
5. 机器不替客户做商业决定，人不需要重算数字。

## 2. 解决方案

### 2.1 一句话

**四种输入 → 一份统一的行项目 → 一个确定性定价引擎 → 停在人该决定的地方 → 客户模板草案。**

### 2.2 数据流

```text
.eml（正文 HTML 表 / 正文制表符 / .xlsx / .pdf）
   │
   ├─ 模型理解层：判断这是什么单、抽正文条款、标记可疑行（可降级）
   └─ 确定性解析：表头别名归一、逐行映射、写入 evidence{file, container, sheet, row, column, raw}
   │
   ▼
RFQ：单据级字段 + 行项目 + 客户随附要求（两条路产出同一个结构）
   │
   ├─ 契约校验：每行有结果、来源可追、金额 = q2(单价 × 数量)
   ├─ 单据质量检查：重复料号、单位混用、缺字段、交期异常（只提示，不改价）
   ▼
定价引擎：候选装配 → 硬约束过滤（件状 / 证书 / 单位 / 件号 / 时效）→ 加成与比价 → 复核项
   │
   ▼
人工预审：有阻塞项就停在 awaiting_review，答完才继续，revision 递增
   │
   ├─ 业务规则核查：逐行 5 条规则记录 pass / warn / fail / not_applicable
   ▼
询价分析报告 DOCX（每单必出）  +  报价草案 DOCX（可报价时）
   │
   ▼
人工批准（具名）→ 单事务写入历史报价表 → quote-r<rev>.docx
```

### 2.3 六步工作台

界面就是这条流水线的显影，不是另做的演示页：

| 步骤 | 系统做什么 | 人看到什么 |
|---|---|---|
| ① 输入采集 | 锁定输入版本，记录载体、客户、询价号、评估日 | 原件链接、客户随附要求原文、模型理解结论、执行轨迹 |
| ② 结构提取 | 四种载体归一成行项目 | 每行的料号 / 数量 / 单位 / 件状 / 截止 + 原始值 + 原件位置 |
| ③ 询价分析 | 查数据快照、装配候选、执行硬约束 | 每行「有依据 / 待预审 / 阻断」+ 单价金额或原因 + 定位 |
| ④ 人工预审 | 生成阻塞项与选项 | 待预审卡片（问题、选项、依据、定位），清空后才放行 |
| ⑤ 分析报告 | 汇总处置结果、逐行原因与建议动作 | 已报价 / 待确认 / 转询价 / 不报价 + 规则核查统计 |
| ⑥ 报价草案 | 填官方模板、算大写、写依据页 | 草案 DOCX 下载；演示模式下可「演示批准并写入历史」 |

### 2.4 五道闸门（任何一道不过，都不出价）

1. **模型理解**——只产出结构，不产出数字；未配置或失败时自动回退确定性解析，并在执行轨迹里写明实际走了哪条路。
2. **契约校验**（`evaluation.validate`）——每行必须有结果、来源可追、金额等于 `policy.line_amount()` 的四舍五入结果。
3. **单据质量**（`quality.inspect`）——重复料号、单位混用、缺优先级、交期早于评估日；整列全空按"该载体不含此列"记录，不当缺陷。
4. **业务规则**（`business_rules.check_business`）——件号匹配、证书、单位、件状、报价截止，逐行逐规则留痕。
5. **人工预审 + 具名批准**——阻塞项未答完不能生成草案；批准只接受具名的人，拒绝 `system:*` 与自动默认答案。

### 2.5 人机边界

| 机器做 | 人做 |
|---|---|
| 解析、归一、识别四种载体 | 决定没有依据的行怎么办 |
| 按件状集合过滤候选、算加成、比价 | 决定要不要放宽件状 |
| 标出重复料号、单位混用、缺优先级 | 判断这些不一致是否影响本次报价 |
| 生成复核问题与 2–3 个明确选项 | 从给定选项里选一个 |
| 填模板、算大写、写依据页 | 对外发送前复核最终价格 |

这条边界是产品的一部分：**机器不替客户做商业决定，人不需要重算数字。**

### 2.6 三个设计取舍

1. **价格只有一个来源。** 所有数字来自 `domain/pricing.py` 的纯函数；模型只能调工具，不能算数。对话助手拿到的也是引擎结果，且载荷被压缩分页（不塞 122 行原始数据）。
2. **复核项按目标寻址。** `RI-0016` 指第 16 行，`RI-TASK` 指整案；答完不重新编号（否则决策日志会指向错的对象）；改一个答案只重算受影响的行。
3. **没有依据就说没有。** 122 行的单如果参考表里没有这些料号，系统只产生**一个**任务级问题（"整体转人工询价"），而不是刷 122 个对话框；小计显示 `—` 而不是 `¥0.00`。

## 3. 技术栈

| 层 | 选型 | 为什么 |
|---|---|---|
| 语言 | Python 3.11+（实测 3.12.9），标准库优先 | 评委环境零安装即可跑通按钮流程 |
| Web 服务 | `http.server`（单进程、线程化请求） | 无 Flask/FastAPI 依赖，单文件路由可读可审 |
| 前端 | 单文件 `index.html` + 原生 JS | 无构建步骤、无 CDN、无外部字体 |
| 存储 | SQLite（`runtime/rfq.db`） | 价格 / 成本表只在源文件变化时读一次，之后按料号索引查询 |
| 表格 | openpyxl | 读四种载体、写导出都用得上 |
| 文档 | python-docx | 直接在客户官方模板上填充，保留格式与样式 |
| PDF | 自研 `ingestion/pdf_text.py`（纯标准库） | 官方 PDF 是 Helvetica + 显式 `Tm` 定位、无压缩流，按 y 分行、x 排序列即可重建表格；不依赖 pypdf，也不假装能解任意 PDF |
| 模型层 | Genesis（OpenAI 兼容）`deepseek-v4.1-flash` | 只做理解与工具选择；未配置时整体禁用，按钮流程不受影响 |
| 测试 | `unittest`，**173 个用例** | 无 pytest 依赖，`python -m unittest discover -s tests` 一条命令复现 |
| 部署 | `Dockerfile` + `render.yaml` + `GET /healthz` | 认 `PORT` / `RFQ_HOST`，收到 SIGTERM 正常退出 |

**依赖可缺省**：`.deps/` 本地缓存、`pip install -e ".[documents]"`、或系统已装，三条路走同一个 `infrastructure/deps.py`。

## 4. 创新点

1. **四种载体，一条映射，证据落到单元格。**
   正文表格、制表符、xlsx、pdf 归一到同一套列名，因此只有一份 `row → Line` 映射。每行带 `evidence{file, container, sheet, row, column, raw}`，界面第 ② 步与第 ③ 步都能点开看到"这行来自哪个文件、第几行、哪一列、原值是什么"。评委可以拿原始 Excel 逐格对。

2. **模型负责"读"，代码负责"算"，中间隔着逐字段校验。**
   模型只产出结构：每个字段带 `value / raw / anchor / confidence`。代码随后证明它是真的——料号与数量必须能在它声称的那一行里原样找到（允许空格 / 连字符差异），数量必须能解析为正小数；置信度 ≥ 0.95 直接采用，0.70–0.95 采用但标记待确认，< 0.70 **拒收**（不猜）。认不出的列进 `unknown_columns`，读不懂的行进 `unparsed_rows`，不静默丢弃。算术只发生在 `pricing.py`。
   这条路径是可核对的：模型失败会回退确定性解析，并把这件事实写进任务轨迹。

3. **人工闸门按目标寻址，答应一个只重算一行。**
   复核项 ID 由目标推导（`RI-0016` = 第 16 行，`RI-TASK` = 全案），答完不重新编号，决策日志始终指向同一个对象；改一个答案只重算受影响的行，`revision` 递增，其余行已定的价不动。

4. **每单必出「询价分析报告」，包括不能报价的单。**
   转询价、不报价同样是工作成果。`reporting/analysis.py` 为每个任务生成 `analysis-r<rev>.docx`：逐行状态、原因、**建议动作**（向供应商询价 / 与客户确认单位 / 要求 FAA 8130-3 …）、定位，以及 5 条规则的核查统计。标题永远是「询价分析报告」，从不是「报价单」。

5. **合规门写在定价路径里，不是写在文档里。**
   客户「询价产品要求」逐行进入定价：`CERT REQUIRED` / 适航类只接受 **EASA Form 1 / FAA 8130-3**（PMA、CoC 判 `cert_mismatch`）；库存表没有证书记录时判 `cert_unverified`，不能自证满足；`SPECIAL REQUIREMENT` 内容未说明则单列待确认；单位按原文比较（PDF 的 `Each / PCS / SET` 不改写成 `EA`），不一致进复核、**不换算**；件号先精确匹配，再按大小写 / 空格 / 横杠归一或 MPN / 手册件号匹配，非精确匹配必须人工确认；即使 PMA 件是最低价，也必须人点头才能采用。

6. **不可欺骗的空结果。**
   没有价格依据时返回 `null`、界面显示 `—`、只问一个任务级问题。这比"给个看起来合理的数字"难做，但它是这套系统能不能被信任的分界线。

## 5. 使用说明

### 5.1 评委最快路径（约 2 分钟）

1. 打开链接（无需登录）。左侧「收件箱」已预置样例 **B**（Excel 附件，21 行）。
2. 点右上「**运行新任务**」——系统解析、定价，然后自己停在「④ 人工预审」，状态胶囊显示「待确认 2」。
3. 在第 ④ 步把两个问题各点一个选项 → 「⑥ 报价草案」出现「生成报价草案」→ 下载 DOCX。

想换输入：左侧「演示素材」列出其余五封官方邮件，点一下会问「打开已有任务 / 作为新任务运行」；也可以把任意 `.eml` 拖进虚线框（先出导入预览，确认后才建任务）。

### 5.2 本地运行（30 秒，离线可用）

```powershell
python -m rfq_agent.web --port 8765     # 浏览器打开 http://127.0.0.1:8765/
```

或双击根目录 `start.cmd`：自动检查 Python ≥ 3.11、缺依赖时自动 `pip install -e ".[documents]"`、启动并打开浏览器。首次启动收件箱只有样例 B，其余素材在「演示素材」里点选导入。

### 5.3 六步分别看什么

| 步骤 | 该看到的 | 证明了什么 |
|---|---|---|
| ① 输入采集 | 客户、询价号、载体、评估日、原件链接、客户随附要求原文、模型理解结论、执行轨迹 | 系统知道自己在处理哪封邮件；条款原文可查 |
| ② 结构提取 | 每行字段条 + 评审标记 + 原始值 + 原件位置（`attachment-xlsx · 第 2 行`） | 提取可逐格核对，不是黑箱 |
| ③ 询价分析 | 每行「有依据 / 待预审 / 阻断」、单价金额或原因、邮件 / 附件 / 表 / 行 / 列 / 原值 | 每个价格都能指回来源 |
| ④ 人工预审 | 阻塞项卡片：问题、2–3 个选项、「看依据」、定位；另有「已通过」页签 | 需要人决定的只有这些，且给出可选动作 |
| ⑤ 分析报告 | 已报价 / 待确认 / 转询价 / 不报价统计、逐行原因与建议动作、规则核查 | 无论能否报价，都有可执行交付物 |
| ⑥ 报价草案 | 草案 DOCX 下载、客户要求核对表、批准戳（演示批准） | 输出是客户模板，且明确标注"待复核" |

### 5.4 六个官方案例（评委会拿它对照）

| 案例 | 载体 | 行数 | 有价格依据 | 待预审 | 解析发现（实测） |
|---|---|---|---|---|---|
| A | 正文 HTML 表格 | 122 | 109 | 22 项 | 9 组同询价号重复料号（9 行重复）、5 个料号跨询价号出现、EA 116 行 / IN 6 行、34 行缺优先级 |
| B | Excel 附件 | 21 | 19 | 2 项 | 1 个料号跨询价号出现（独立询价行，不按重复处理）、EA 20 行 / IN 1 行、6 行缺优先级 |
| C | PDF 附件 | 7 | 0 | 1 项（任务级） | 件状与截止日期两列整列为空（记为"该载体不含此列"）、单位 `Each` ×7、7 条客户要求 |
| D | 正文表格 | 122 | 0 | 1 项（任务级） | EA 115 行 / FT 7 行、30 行缺优先级 |
| E | Excel 附件 | 21 | 0 | 1 项（任务级） | EA 20 行 / FT 1 行、5 行缺优先级 |
| F | PDF 附件 | 7 | 0 | 1 项（任务级） | 同 C：件状与截止日期整列为空、单位 `Each` ×7、7 条客户要求 |

**C/D/E/F 为什么 0 行有价**：两张参考表覆盖的是 `PN-*` 料号与标准件（`NAS`/`MS`/`AN`），而 C/F 是 `GSK-*`/`CPL-*`、D/E 是 `AP-*`。7 行、122 行都完整解出来了，是**确实没有价格依据**。系统的正确行为是说出来：只产生一个任务级问题（"整体转人工询价"），小计显示 `—`。

**效果（实测）**：样例 B 点「运行新任务」→ 4.6 秒停在「待确认 2」→ 答两项 → 生成分析报告与报价草案；样例 A 解析 0.05 s + 定价 0.03 s + 模型理解 13 s，停在 22 个待预审项。四种输入走的是同一条定价、预审与导出链路，只有一份 `row → Line` 映射。

### 5.7 降级与故障

## 6. 数据合规说明（命题赛道）

### 6.1 数据来源与范围

- **仅使用赛事提供的演示 / 脱敏数据**：`data/询价信息素材/`（6 封 `.eml` + 2 个 PDF + 2 个 xlsx）、`价格资源表_演示数据.xlsx`（342 行）、`内部物料成本表_演示数据.xlsx`（163 行）、`报价单样例.docx`。
- 客户名称为「客户A / 客户B」「Buyer C」，域名形如 `.test`；**不含真实客户、供应商、价格或个人信息**。
- 不使用任何来源不明的第三方数据；不抓取公开网页；不做竞品数据核对。

### 6.2 数据分类与去向

| 数据 | 存在哪 | 是否离开本机 |
|---|---|---|
| 询价邮件与附件 | `runtime/uploads/`、`runtime/<task_id>/`、SQLite | **是**：可读文本块发往模型接口做理解（见 6.4） |
| 价格资源表 / 内部成本表 | `runtime/rfq.db`（只读快照，按哈希只增不改） | **否**，价格计算全部本地完成 |
| 任务、决策日志、历史报价 | `runtime/`、SQLite | **否**；对话助手只接收任务摘要 |
| 导出的 DOCX | `runtime/<task_id>/` | **否**（由用户自行下载） |

### 6.3 用户上传文件

- 只接受 `.eml`；落在服务实例的 `runtime/uploads/`，解析结果写入本机 SQLite。
- 预览阶段先存到 `runtime/uploads/.pending/`（不进入素材扫描、不建任务）；未确认的预览在服务重启时清理。
- **不转发任何第三方、不进共享库、不做二次分发**；不做跨实例同步、不云备份。
- 上传前有导入预览（行数、载体、解析发现），用户确认后才创建任务；解析失败的文件不建任务。
- 删除方式：删除 `runtime/uploads/` 与对应任务目录即可；免费实例重建后自动清空（无持久盘）。

### 6.4 模型调用

- **目的**：判断邮件是否为询价单、抽取正文中的报价条款、标记可疑行；以及对话助手选择工具。
- **发送范围**：该封邮件的可读内容块（正文文本、表格单元格、PDF 文本行），单次不超过 400 行、分页 50 行。
- **不发送**：价格资源表、内部成本表、历史报价、其他任务数据、任何凭据或个人信息。
- 服务方为赛事提供的 Genesis 网关（OpenAI 兼容接口），**仅用于本次推理，不用于训练**；请求体不落盘，仅记录模型名与耗时。
- 未配置 token 时该层整体不启用，产品功能不受影响（见 §5.7）。

### 6.5 凭据、日志与访问控制

- 访问令牌只存在于服务端环境变量；`.env` 已在 `.gitignore` 中，仓库不含 token；前端、导出文档、页面日志均不展示。
- 页面只显示文件名，不显示绝对路径；访问日志仅记录请求路径与状态码，无请求体。
- 演示链接无账号体系：任何人拿到链接即可试用，但因为**全部是演示数据**，不构成真实信息泄露。

### 6.6 输出定位与责任边界

- 所有 DOCX 首页与备注均标注「**待复核草案**」，声明税费、运费未计入，不预留库存。
- 系统**不代发邮件、不自动下单、不对外承诺价格**。
- 最终价格、件状放宽、超额采购、无依据转运维、PMA 件采用，五项必须由具名的人确认（见 §7）。

### 6.7 保留期限与销毁

- 演示数据与任务记录仅保留在实例本地，评审期内有效；评审结束后可整体销毁实例或删除 `runtime/`。
- 不向任何第三方归档、不出售、不交换数据。

### 6.8 第三方组件

- `openpyxl`（MIT）、`python-docx`（MIT）、`lxml`（BSD）：仅本地运行，不联网。
- 无统计、埋点、广告或分析 SDK；**唯一出站请求**是配置的模型接口。

## 7. 已知限制与人工确认边界

| 限制 | 现状 | 影响 / 应对 |
|---|---|---|
| 公网实例 | 已部署在 Render 免费版（Docker + `/healthz`），2026-11-10 公网实测全流程通过 | 免费实例 15 分钟休眠，首次访问需等 30–60 秒冷启动 |
| PDF 解析 | 只支持官方那种「Helvetica + 显式 `Tm` + 无压缩流」表单 | 其他 PDF 明确报错而非猜测；通用场景需换 pypdf / 版式识别 |
| 价格覆盖 | 342 行只覆盖 `PN-*` 与标准件 | C/D/E/F 为 0 行有价，属数据事实 |
| 条款回灌 | 已核对「草案是否满足客户要求」，但未回灌定价策略（如"有效期 30 天"未改变报价有效期计算） | 需人工按条款确认 |
| 多用户 | 单进程 SQLite，串行写 | 不适合并发压测；评审演示足够 |
| 出口管制 / 合规判定 | 只做提示，不自动判定 | 需人工确认 |
| 模型延迟 | 单次理解 5–13 s，`qwen3.8-max` 曾超时 | 模型是可选增强层，按钮流程不依赖 |

**人工确认边界（不可让渡）**

1. 件状放宽（客户要 FN，现货是 SV/OH）；
2. 按 MOQ 超额采购；
3. 无价格依据时转人工询价还是弃标；
4. 对外发送前的最终价格与有效期；
5. PMA 件（即使价格最低）是否采用。
