## 1. 文档定位

本文描述 RFQ 询价分析与报价智能体的产品方案和技术架构。通用 Schema、规则协议、处理状态与商业处置以《RFQ 行业无关基准设计》为准；航空素材是第一套扩展 fixture，不定义通用产品边界。赛事素材中的客观事实以《RFQ赛题解析》为准；本文只负责说明如何实现，不重复定义赛事事实。业界流程对标与差异分析见 [RFQ_INDUSTRY_BENCHMARK.md](./RFQ_INDUSTRY_BENCHMARK.md)。

定位说明：本项目站在**供应商侧报价**（supplier-side quoting），不是买方 e-sourcing 比价。因此对标对象是 CPQ / quote-to-order，而不是采购比价平台。

## 2. 方案结论

项目应实现一个“证据驱动的 RFQ 报价工作台”，而不是普通聊天机器人：

```text
六个官方 RFQ 请求
→ 邮件与附件解析
→ 统一 RFQ 数据模型
→ 完整性和冲突检查
→ 内部库存/成本与供应商报价匹配
→ 确定性候选过滤和报价计算
→ 主智能体解释、追问和组织结果
→ 人工确认
→ 动态生成报价草案
```

Deep Agents 负责编排和异常处理；本地代码负责解析、校验、匹配及计算；MatrixOrigin Genesis 提供模型能力；MOI Workflow、Catalog 和 Agent 在验证稳定后承担平台展示和交互。

## 3. 产品目标与边界

### 3.1 目标用户

- 收到客户 RFQ 的销售人员；
- 报价专员；
- 需要核对供应来源和履约条件的供应链人员。

### 3.2 核心用户任务

用户提交一封 RFQ 邮件及其附件，系统完成：

1. 识别输入模式；
2. 提取 RFQ 基本信息和全部行项目；
3. 标记缺失、重复、冲突和异常；
4. 查询内部库存/成本和供应商价格；
5. 过滤不满足业务条件的候选；
6. 根据透明配置形成报价建议；
7. 展示数据来源、计算过程和风险；
8. 自动生成标明待复核的报价草案；用户确认后生成已复核版本。

### 3.3 非目标

- 自动收取真实邮箱邮件；
- 自动对外发送正式报价；
- 无人工确认的自主定价；
- 实时向外部供应商询价；
- 复杂审批、ERP 或 CRM 集成；
- 汽车模具或工业图纸报价；
- 为展示技术复杂度而构造多智能体系统。

## 4. 分阶段产品范围

### 4.1 V0：两条垂直切片

实测覆盖率（《RFQ赛题解析》§4.5）显示只有 B 能验证完整报价链路，因此 V0 拆成两条切片，分别验证“解析可信”和“报价可复算”。

**V0a（Buyer C）— 解析与条款切片**

```text
解析英文邮件 + Quote.pdf
→ 得到 RFQ-0930、Respond by 2026-09-15、7 个行项目（GSK-001…GSK-007）
→ 全部行无价格依据，输出 7 行 needs_review + 理由 no_price_basis
```

退出条件：7 行不漏；字段与来源可定位；报价列全空且不伪装为 0。

**V0b（客户 B）— 报价链路切片**

```text
解析邮件 + 询价报价清单.xlsx
→ 21 行 / 20 个料号全部命中参考表
→ 19 行可报价（5 行用内部库存、14 行用供应商），2 行转人工
→ 生成动态行数的 DOCX 草案
```

退出条件：料号 100% 命中；候选与拒绝理由逐行可读；数字可由人工复算；2 行人工项理由正确（PN-0015、PN-0018：内部件状 NE 不符 FN，供应商 MOQ 超额）。

V0a 证明“不编价”，V0b 证明“能报价”，两者都完成才算 V0 通过。V0 仍是开发切片；六案例覆盖是项目自设的 MVP 质量目标，不表示赛事明文要求六例全部通过。

### 4.2 V1：第一组开发集

覆盖第一组客户 A、B、C，验证三个输入子型：

- 正文-拼接型（A，无分隔符，需锚点切分）；
- 邮件 + Excel（B，完整报价链路）；
- 英文邮件 + PDF（C，解析与条款，无价格依据）。

D 的正文-制表符型作为第四个输入子型在 P3 与第二组一起回归。

### 4.3 MVP：两段式闭环

第一组作为开发集，第二组作为回归集。六个请求全部进入同一 RFQ Schema，但闭环分两段：

- **解析-校验闭环 6/6**：六个请求都能完成解析、标准化、异常识别，并产出可追溯的结构化结果；
- **候选-报价闭环 2/6**：只有 A、B 有价格依据（《RFQ赛题解析》§4.5），C/D/E/F 的正确结果是全行 `needs_review` + 无价格依据。

四例零覆盖是素材事实，不是实现缺陷。验收时不得把“四例无报价”判为失败，也不得为了凑齐六例而编造价格或放宽为模糊匹配。

### 4.4 比赛交付版

在两段式闭环（解析 6/6、报价 2/6）之上增加：

- 可公开访问的智能体入口；
- 可视化处理状态；
- 报价草案下载；
- 平台能力说明；
- 三分钟演示视频；
- 公开说明文档和数据合规说明。

## 6. 核心工作流

### 6.1 任务状态

```text
received
→ parsing
→ normalizing
→ validating
→ matching
→ pricing
→ needs_review / ready
→ generating
→ completed
```

失败状态：

```text
needs_input | partially_completed | failed
```

> 实现状态：骨架目前只有 `received → analyzed → needs_review` 三个显式状态（`rfq-agent/rfq_agent/service.py`），上图是目标态。P1 前必须收敛到上图，或在本节补一张“当前状态 → 目标状态”映射表，避免验收时对不上账。

### 6.2 详细流程

1. **接收任务**：创建任务 ID，保存原始文件和文件摘要。
2. **邮件解析**：读取发件人、主题、日期、正文、附件名称和二进制附件。
3. **输入分类**：判断明细位于正文、Excel 或 PDF。
4. **附件解析**：保留原始行、表格位置、页码等来源信息。
5. **字段标准化**：映射为统一 RFQ Schema，保留原始值和规范值；重复行只标记，不自动合并或删除。
6. **质量检查**：检查缺失、重复、冲突、类型、日期和单位。
7. **候选匹配**：按 Part Number 查询内部物料和供应商价格。
8. **硬约束过滤**：有效期、MOQ、数量、件状、证书、交期和币种。
9. **候选排序**：应用明确配置，不允许模型自由决定权重。
10. **报价计算**：由确定性函数产生价格、金额和计算解释。
11. **智能体审阅**：整理结果、解释异常、生成需要人工回答的问题。
12. **人工确认**：确认低置信度字段、替代件、过期参考价及正式报价。
13. **产物生成**：生成动态行数的报价草案和完整决策记录。

### 7.5 报价单模板字段映射

官方模板明细表实测为 9 列 × 5 个空白明细行，**没有单价列、没有税率列、没有币种和汇率列**。决策模型的四个金额字段必须按固定规则落到模板：

| 模板列 | 来源字段 | 说明 |
|---|---|---|
| 序号 | `line_number` | |
| 产品名称 | `description` | |
| 型号 | `part_number` | 模板无“料号”列，用型号承载，须在说明文档中写明 |
| 规格 | `product_scope` | 可空 |
| 数量 | `quantity` | |
| 单位 | `unit_of_measure` | |
| 金额 | `recommended_unit_price` | 单价，Decimal，HALF_UP 保留 2 位 |
| 销售总价（元） | `line_total` | 行小计 = 单价 × 数量 |
| 备注 | `warnings` / 未计入说明 | 税、运费、包装费、关税、汇率缓冲的显式落点 |

- `总金额（大写 / 小写）`：仅当全部行都有价格时填写；存在未报价行时填“部分报价，见备注”，不得填 0。
- 模板中的“销售总价（元）”与“总金额”语义重叠：行内保留行小计，表尾“总金额”填已报价行小计之和。
- 模板无法承载币种与税率，故 `charges` 类配置统一以"未计入"文字写入备注，并与 `policy_version` 一起显示。
- **附加一页"报价依据与条件摘要"**（PDF 或 DOCX 附页，不修改官方模板）：逐行件状、证书、追溯要求、可售数量、交期天数、MOQ、发货国、价格有效期；整单币种、Incoterms、报价有效期、"本报价不预留库存"声明、"税费运费未计入"声明。理由：业界可比报价必须含这些要素，而官方模板没有对应列（见《RFQ_INDUSTRY_BENCHMARK》§3.3）。

## 8. 报价规则引擎

### 8.1 硬约束

候选出现以下情况时默认不可直接使用：

- Part Number 不匹配；
- 价格状态无效，或有效期早于评估日期（须两者同时满足才可用；冲突时分记 `status_invalid` / `date_expired` 并保留两个原值）；
- 请求数量低于 MOQ 且不允许按 MOQ 采购；
- 可用库存不足且不允许拆单；
- 件状条件不满足——判定为"候选件状 ∉ 客户可接受集合"，不是等值比较；客户可能给多个可接受件状（如 NE、NS、OH），优劣由配置化偏序决定，不硬编码行业默认排序；集合缺失时记 `unknown` 并转人工；
- 必需证书不满足；
- 交期晚于客户要求；
- 币种或汇率缺失，无法得到统一成本。

### 8.2 候选排序

赛事未给出正式排序规则，第一版使用配置驱动策略。建议默认顺序：

1. 满足全部硬约束；
2. 数据仍在有效期；
3. 内部库存或供应商能够满足数量；
4. 统一币种成本更低；
5. 交期更短；
6. 稳定候选 ID 决胜，保证排序可重复。

内部库存是否优先、是否允许拆单以及成本口径均为待确认配置，不写死为赛事规则。

### 8.3 报价计算

第一版采用透明公式：

```text
报价单价 = 选定成本基线 × (1 + 加价率)
行金额 = 报价单价 × 报价数量
```

税费、运费、包装费、关税、汇率缓冲和价格取整分别配置。缺少配置时应显示“未计入”，而不是隐式假定为零。

### 8.4 人工确认边界

以下情况必须转人工：

- 没有合格候选；
- 只能使用过期价格；
- 多来源数据冲突；
- Part Number 模糊匹配；
- 件状或证书不完全一致；
- 需要拆单或替代料；
- 汇率、税费或额外费用缺失；
- 模型提取字段置信度不足；
- 正式对外报价。

## 9. Deep Agent 设计

### 9.1 为什么使用 Agent

输入载体、缺失信息和异常路径并不固定，需要根据当前状态选择解析、查询、补充信息或人工确认动作。Agent 的价值在于编排这些动作，而不是替代规则引擎。

### 9.2 第一版工具

| 工具 | 输入 | 输出 | 性质 |
|---|---|---|---|
| `inspect_input` | 文件列表 | 文件类型和处理建议 | 只读 |
| `parse_email` | EML 路径/内容 | 邮件元数据、正文、附件 | 只读 |
| `parse_spreadsheet` | XLSX | 表格、字段和来源 | 只读 |
| `parse_pdf` | PDF | 文本、表格、页码 | 只读 |
| `normalize_rfq` | 解析结果 | 统一 RFQ JSON | 确定性优先 |
| `validate_rfq` | RFQ JSON | 问题列表和严重度 | 确定性 |
| `find_internal_materials` | Part Number | 内部库存/成本候选 | 只读 |
| `find_supplier_quotes` | Part Number | 供应商候选 | 只读 |
| `evaluate_candidates` | RFQ 条件、候选、配置 | 合格/拒绝候选及理由 | 确定性 |
| `calculate_quote` | 选定候选、配置 | 单价、金额和计算轨迹 | 确定性 |
| `generate_quote_draft` | 已确认决策 | DOCX/XLSX/PDF 草案 | 写产物 |
| `request_human_review` | 问题及选项 | 待确认状态 | 人机协作 |

以上为内部函数清单。Agent仅暴露 `analyze_rfq`、`build_quote_options`、`apply_review`、`export_quote_draft`、`get_task_result` 五个业务工具，契约见开发计划。工具返回结构化对象，大量原始内容保存在任务文件中。

### 9.3 暂不使用子智能体

第一版不启用子智能体。只有满足以下证据之一才引入：

- 并行解析明显降低总耗时；
- 不同输入模式需要相互隔离的长上下文；
- 主智能体上下文被大量解析结果污染；
- 回归评测证明专用 Agent 提升准确率。

## 10. MatrixOrigin 集成

### 10.1 必选集成

- Genesis：作为模型服务；
- MOI Agent 或兼容的公开入口：作为最终展示候选。

### 10.2 条件集成

- Workflow：当附件输入、节点调试和 Agent 绑定稳定时使用；
- Catalog：当 Excel 导入和结构化查询稳定时承载数据表；
- 知识层：先建设版本化规则目录，再按需要接入政策、术语和说明资料的检索；不先建设航空专用知识库，也不允许检索文本直接参与价格计算。行业知识通过扩展包注册 Schema、规则、术语和验收 fixture。

### 10.3 降级路径

已观察到 Excel 导入 HTTP 400。任何平台能力接入前必须通过独立验证，失败时保持：

```text
本地解析和报价服务
→ Genesis 模型调用
→ 自建公开 Web UI 或 MOI Agent 展示
```

核心业务测试不得依赖 MOI 页面操作。

## 11. 可靠性与可追溯性

每次任务至少保存：

- 原始文件摘要；
- 解析器版本；
- 标准 RFQ JSON；
- 字段来源；
- 原始候选数据；
- 每个候选的过滤理由；
- 使用的报价配置版本；
- 计算轨迹；
- 人工确认记录；
- 最终产物和生成时间。

相同的已校验 RFQ、业务数据快照、报价参考时间和规则版本，必须产生相同报价数字。模型重新提取可能波动，应独立评测提取稳定性；不要承诺从原文件起每次模型运行都完全相同。

## 12. 安全与数据合规

- 第一版只使用赛事提供的演示/脱敏数据；
- API Key、访问令牌和个人账号信息不得进入仓库、日志、截图或演示视频；
- 上传文件只用于当前任务，不用于未经授权的模型训练；
- 对外报价必须经人工确认；
- 解析失败时不将原始敏感内容直接回显到错误页面；
- 任务范围内保存中间结果和生成草案无需逐次确认；修改业务事实、确认正式报价或外部发送才需要确认。第一版不实现外部发送。

## 13. 验收策略

### 13.1 数据集划分

- 第一组 A/B/C：开发和调试；
- 第二组 D/E/F：固定回归验证。

### 13.2 核心指标

- RFQ 单据字段准确率；
- 行项目召回率和字段准确率；
- 来源追溯覆盖率；
- 异常识别召回率；
- 候选过滤规则正确率；
- 报价计算一致性；
- 六案例端到端成功率；
- 单案例处理时延和模型消耗。

### 13.3 最低验收

以《RFQ赛题解析》第 9 节六案例矩阵为最低事实标准，并增加：

- 所有报价数字有来源或公式；
- 不合格候选不会进入自动报价；
- 无可靠依据时转人工；
- 报价草案支持动态行数；
- 回归集未被写死或作为提示词示例泄漏；
- 无价格覆盖的案例（C/D/E/F）正确结果是全行转人工，不得为凑齐行数而留空、填 0 或改用模糊匹配。

## 14. 关键配置

```yaml
# 以下全部是方案假设。素材没有给出任何定价规则，故每一项都必须视为可配置策略，
# 在报价输出中与 policy_version 一起显示，不得表述为赛事规定。
pricing:
  cost_basis_priority: [standard_cost, supplier_price]   # 内部标准成本优先；不足或过期时用供应商价
  internal_inventory_priority: true                      # 内部优先，但仅当库存数量与件状同时满足
  default_markup_rate: "0.20"                            # 成本 100 → 报价 120；毛利率口径另算
  rounding_mode: HALF_UP
  price_decimals: 2
  quote_validity_days: 30                                # 且不得超出选定供应商价格有效期
  allow_split_fulfillment: false
  allow_moq_overbuy: false
  allow_expired_price_reference: false

delivery:
  lead_time_tolerance_days: 0                            # 客户未给交付期时，不据此拒绝候选

currency:
  base_currency: CNY
  fx_to_cny: { CNY: "1", EUR: "7.75", USD: "7.1" }       # 素材实测，方向为外币 → CNY
  missing_exchange_rate_action: human_review

charges:
  tax_policy: excluded_and_stated                        # 模板无税率列，一律写明“未计入”
  shipping_policy: excluded_and_stated
  packaging_policy: excluded_and_stated
  tariff_policy: excluded_and_stated
```

以上均为方案假设（非赛事规则），须与配置版本号一并记录并在报价输出中可见。未计入的税费、运费、包装费和关税必须在报价单备注中显式写明“未计入”，不得隐式当作零。
