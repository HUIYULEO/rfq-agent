# RFQ 智能体评估报告：我们想做什么，代码实际做了什么

> 日期：2026-11-03　|　评估对象：rfq-agent 当前代码（122 个单测全部通过）　|　读者：产品负责人、业务方、工程团队

---

# 第一部分　结论（不审代码也能读完）

## 1.1 一句话

**这套系统现在是一个"格式固定的单据处理器"，还不是一个"能读懂客户来信的询价助手"。**

它对六个官方样例跑得很好；从第七封真实客户邮件开始就会失效——而且**失效时不报错，那封邮件会直接消失**。

## 1.2 现在像什么

像一台**只认一种模板的扫描仪**：客户按我们的模板填，一扫就出报价；稍换写法（"数量"写成"Qty"、明细放第二个 sheet、要求写成段落而不是编号），就**扫不出来**，而且不提示"没看懂"，是当这封信不存在。

真正的询价助手应该像有经验的报价员：先看信、判断是什么、找到表格在哪、分清哪句是要求哪句是备注，看不懂就**主动来问**。

## 1.3 四个问题的严重度

| # | 问题 | 判定 | 严重度 | 业务后果 |
|---|---|---|---|---|
| 1 | 输入获取不明确，靠写死应对六个情况 | **成立**。写死的不是案例清单，是四台解析器，比清单更刚性 | 🔴 致命 | 只能演示不能上线；第一个真实客户就可能完全进不来，且不报错 |
| 2 | 只比结构化字段，未考虑备注/利润/交期/运费/重量/发货地 | **成立**。引擎只做"合规过滤"，不做"生意" | 🔴 严重 | 算出来的不是能报的价；一半以上的商务条款被读进来又扔掉 |
| 3 | 审核流程与人工知识如何获取、不确定如何处理 | **部分成立**。门禁很扎实，但"人"只在答选择题，知识不沉淀 | 🟠 中偏重 | 同一问题第 101 次出现还要人再答；多条件冲突无法同时处理 |
| 4 | 报价生成与多语言 | **成立**。是模板填充器，不是报价生成器 | 🟠 中等 | 英文客户拿到全中文单据；单价填在"金额"列；无多币种 |

## 1.4 每一块的一句话

- **输入**：六封样例之外的邮件基本进不来；进来了也看不懂变体。
- **分析**：会判断"这货能不能卖"，不会判断"这单划不划算"。
- **审核**：问得很规范，问完就忘。
- **产出**：能把数字填进格子，但填错了格子，且只有中文人民币一种形态。

## 1.5 最大的风险

> **最大的风险不是"功能少"，而是"失败是静默的"。**
>
> 一封格式不符的客户邮件，不显示解析失败、不进待处理列表、不通知任何人——它从收件箱里消失了。演示时看不出来（有六个准备好的样例），上线第一天就会出事。

## 1.6 需要多少工作量

| 阶段 | 内容 | 工作量 | 不做会怎样 |
|---|---|---|---|
| P0 | 输入层改为"模型理解 + 校验兜底" | 约 13 人日 | 产品不成立，只能演示 |
| P1 | 补齐商务维度（备注/毛利/交期/运费） | 约 22 人日 | 报价不可用 |
| P2 | 审核知识沉淀 + 多语言多币种 | 约 24 人日 | 无法规模化，每个新客户重新配 |

**最低可交付：P0（13 人日）。** 只做 P1/P2 不做 P0，等于给一台扫不出图的扫描仪加美颜。

# 第二部分　逐条对照：想做什么 vs 实际做了什么

> 每条给出「目标 / 现状 / 差距 / 影响」，括号内标代码位置供工程复核，业务读者可跳过括号。

## 2.1 输入获取

### 1-1 先判断来信是什么

| | |
|---|---|
| **目标** | 拿到邮件或附件，先判断"这是什么"（询价/报价/对账单/其他），再决定怎么处理 |
| **现状** | 无条件假定是询价单。`ingest_eml()` 一进来就找表格，找不到报错。没有文档分类环节。 |
| **位置** | `rfq_agent/ingest.py:314-338` |
| **差距** | 没有"这是什么"这一层 |
| **影响** | 客户转发一封带历史报价的邮件，会被当新询价解析，可能产出错误数据 |

### 1-2 正文表 + 附件都要看

| | |
|---|---|
| **目标** | 正文汇总表与附件明细合并、交叉校验，冲突时报出来 |
| **现状** | 正文 HTML 表一旦解析成功，**附件完全不看**，连打开都不打开 |
| **位置** | `rfq_agent/ingest.py:319-338` |
| **差距** | 是"二选一"，不是"合并 + 校验" |
| **影响** | 正文 5 行摘要 + 附件 122 行明细，只处理 5 行，且**不提示有附件**。业务方当场就能发现 |

### 1-3 表头用词不同也能认

| | |
|---|---|
| **目标** | `Part Number`/`P/N`/`件号`/`料号`/`物料编码`/`Qty`/`需求数量` 都能识别 |
| **现状** | 硬编码 18 条别名，超出即整封失败 |
| **位置** | `ingest.py:29-45`（别名表）、`ingest.py:46`（必需列）、`ingest.py:111-113`（缺列抛错） |
| **差距** | 覆盖面 ≈ 我们见过的写法 |
| **影响** | `Q'ty`、`QTY (PCS)`、`需求数量` 全部失败。这是"写死"最直接的体现 |

### 1-4 Excel 多 sheet 也能找到明细

| | |
|---|---|
| **目标** | 扫描所有 sheet，判断哪张是明细表 |
| **现状** | 只读第一个 worksheet |
| **位置** | `ingest.py:172` |
| **差距** | 无 sheet 发现逻辑 |
| **影响** | 明细在 sheet2、sheet1 是封面/说明时，读到空表后失败 |

### 1-5 PDF 不限版式

| | |
|---|---|
| **目标** | 支持表格型 PDF、扫描件（OCR）、多栏排版 |
| **现状** | 只有两条正则，专匹配官方 `Quote.pdf` 的排版 |
| **位置** | `ingest.py:185-186`（`PDF_ITEM`/`PDF_QTY`）、`ingest.py:207-236`、`ingest.py:234-236`（缺数量整体抛错） |
| **差距** | 不是"PDF 解析器"，是"这一份 PDF 的解析器" |
| **影响** | 换排版或扫描件即无法处理；而航空业 RFQ 中 PDF 是主流载体 |

### 1-6 PDF 关键信息用语义提取

| | |
|---|---|
| **目标** | 理解哪个是询价单号、哪个是报价截止日、紧急度属于哪档 |
| **现状** | 行首关键字硬匹配：`Report date:`/`Respond by:`/`FOR `/ 整行等于 `CRITICAL`/`AOG`/`URGENT` |
| **位置** | `ingest.py:193-206` |
| **差距** | 换措辞（`Date of issue:`、`Quote due:`、`Aircraft:`）即丢字段 |
| **影响** | 字段丢失**不报错**，静默变空值，下游误以为"客户没提供" |

### 1-7 正文里的报价要求（任意格式）都能提

| | |
|---|---|
| **目标** | "请在报价中包含以下内容"无论编号、项目符号、段落、表格，都能提取 |
| **现状** | 只认 `1.` `2)` 行首编号；PDF 只认 "Remarks" 之后且以句号结尾的行 |
| **位置** | `ingest.py:271`、`ingest.py:288-302` |
| **差距** | `（1）`、`•`、无编号段落三种写法都不支持 |
| **影响** | 要求漏掉 → 报价漏项 → 客户投诉"没按要求报"，属**合同风险** |

### 1-8 解析失败要让人知道

| | |
|---|---|
| **目标** | 失败进"待处理"列表，标红，提示需人工处理 |
| **现状** | 静默跳过 |
| **位置** | `rfq_agent/cases.py:90-94`（`except (ValueError, OSError): continue`） |
| **差距** | 没有失败态、告警、待办 |
| **影响** | **全篇最严重。** 邮件"消失"，业务方以为没收到，客户以为已发出，丢失真实商机 |

### 1-9 让模型理解和抽取，而不是写代码

| | |
|---|---|
| **目标** | 模型通过调用工具（读附件、看表格、分类文档、抽取字段）完成理解，代码负责校验兜底 |
| **现状** | 模型只拿到 **10 个工具**，全是"操作已完成的任务"：`list_cases`/`start_case`/`get_task`/`get_lines`/`explain_line`/`resolve_review`/`export_draft`/`activate_quote`/`get_history`/`record_feedback`。**没有任何工具接受原始输入**。`start_case` 的参数是"案例字母 A–F"，即模型能做的第一件事是**从六个准备好的样例里挑一个** |
| **位置** | `rfq_agent/genesis.py:141-182`、`genesis.py:149-153` |
| **差距** | 模型在流水线**末端**，只"解释结果"，不"理解输入" |
| **影响** | 这是"靠写死应对六个情况"的根源。模型不参与输入端，系统就无法泛化——再写十台解析器也没用 |

### 1-10 接入企业自己的价格表不需要改代码

| | |
|---|---|
| **目标** | 上传或配置数据源即可，表结构变化能被识别 |
| **现状** | 文件名与目录硬编码 |
| **位置** | `cases.py:19-22`（`MATERIAL`/`PRICE_TABLE`/`COST_TABLE`/`TEMPLATE`） |
| **差距** | 没有数据源配置层 |
| **影响** | 每接一个客户就要改代码 + 重新部署，做不成产品 |

> **输入层判定：这是演示级实现，不是生产级实现。** 六封邮件能跑通，是因为解析器就是照着这六封写的。不是缺陷，是**目标选错了**：目标定成了"让六个案例跑通"，而不是"让任意一封信能进来"。能力上限 = 我们见过的格式。

## 2.2 询价分析与商务判断

### 2-1 比较"能不能卖"（合规过滤）

| | |
|---|---|
| **目标** | 件号、数量、件状、证书、单位、MOQ、有效期都核对 |
| **现状** | **✅ 已实现且扎实。** 件号精确/归一化/别名三级匹配；证书按客户原文判定；单位按原文比较不擅自换算 |
| **位置** | `pricing.py:95-272`、`compliance.py` |
| **差距** | 无（系统强项） |

### 2-2 比较"划不划算"（商务判断）

| | |
|---|---|
| **目标** | 成本结构、毛利目标、交付可行性、竞争定价 |
| **现状** | **几乎没有**，只有一个全局 20% 加价 |
| **位置** | `policy.py:17`（`"default_markup_rate": "0.20"`）、`pricing.py:356` |
| **差距** | 唯一档位、不随风险/金额档/客户变化 |
| **影响** | 2 元垫片与 22 万元传感器同样加 20%。低值件利润太薄、高价件失去竞争力 |

### 2-3 供应商备注要参与报价

| | |
|---|---|
| **目标** | "不含税"按含税口径还原；"含包装费"不再重复收；"需预付"写进付款条件 |
| **现状** | 读进来了，然后**扔掉**。`remark` 进了候选对象，无任何代码再读它；报价单备注栏也不含它 |
| **位置** | 读入 `pricing.py:263`；使用：**无**；报价备注 `export_docx.py:141-161` |
| **实测** | 价格表 342 行中 **173 行（50.6%）带影响口径的备注**：批量价另议 34、含包装费 32、含加急服务费 30、价格随汇率浮动 27、不含税 27、需预付 23 |
| **差距** | 知道但不说出去 |
| **影响** | 报价口径可能直接错（把不含税价当含税报）。评审翻到那列就会质疑全部数字。**最容易验证、最伤的一处** |

### 2-4 利润率分档

| | |
|---|---|
| **目标** | 按料号类别、金额档、客户等级、紧急度、风险分设目标毛利 |
| **现状** | 一个全局常量 |
| **位置** | `policy.py:11-22`（整份策略仅 4 个键） |
| **差距** | 没有"毛利策略"，只有一个数字 |
| **影响** | 无法差异化定价；无最低毛利保护线，理论上可报出亏本价 |

### 2-5 交期参与决策

| | |
|---|---|
| **目标** | 交期是硬约束：客户要 5 天，86 天的货源应直接排除或标红 |
| **现状** | 读进来了、显示了、**不参与任何判断**。选供应商唯一排序依据是单价 |
| **位置** | 读入 `pricing.py:257`；写入依据 `pricing.py:340`；打印 `export_docx.py:272`；**筛选/排序：无**（`pricing.py:271` 仅按 `unit_cost_cny`） |
| **差距** | 交期是装饰品 |
| **影响** | 会把"最便宜但 86 天到货"的德国货源推荐给 AOG（紧急停场）客户。航空业这是灾难级错误 |

### 2-6 客户要求的到货日

| | |
|---|---|
| **目标** | 记录"要求何时到货"，据此判断可行性 |
| **现状** | **系统里没有这个字段。** 现有 `截止报价日期` 是"要求我们何时回复报价"，不是到货日 |
| **位置** | `models.py:30`（注释已澄清为"客户回复截止"）；全库无 delivery-date 概念 |
| **差距** | 缺字段，不是缺逻辑 |
| **影响** | 无法回答最基本的问题："这单能不能按时交？" |

### 2-7 优先级（AOG/USR/WSP/NOR）生效

| | |
|---|---|
| **目标** | AOG/USR 应优先选现货、接受溢价、计加急费 |
| **现状** | 解析了、前端显示了、完整性也查了，**定价零使用** |
| **位置** | 解析 `sources.py:76`；前端 `web.py:62`；完整性 `quality.py:68`；定价：**无引用** |
| **差距** | 字段存在但无业务含义 |
| **影响** | AOG 单与常规单，货源选择和价格完全一样 |

### 2-8 运费

| | |
|---|---|
| **目标** | 按起运国、目的国、重量、时效算运费并计入总成本 |
| **现状** | **完全没有**，全库 0 处运费计算；报价单只写一句"税费、运费、包装费口径待企业确认" |
| **位置** | `export_docx.py:244` |
| **差距** | 无运费模型、无费率表 |
| **影响** | 实测 **65.5%（224/342）货源来自境外**（中国 118、美国 88、新加坡 34、挪威 31、立陶宛 28、德国 25、香港 18）。跨境运费被忽略 = 系统性低估成本 |

### 2-9 重量与体积

| | |
|---|---|
| **目标** | 有重量才能算运费、判断空运还是海运 |
| **现状** | **三个数据源都没有这个字段**（价格表 18 列、成本表 14 列、看板 16 列），代码也没有 |
| **差距** | 数据与代码双缺 |
| **影响** | 这是"需要引入额外信息"的真实增量点——必须补一张重量/尺寸主数据表，否则运费永远算不准 |

### 2-10 发货地区

| | |
|---|---|
| **目标** | 起运国影响运费、清关时长、汇率风险、贸易合规 |
| **现状** | 有字段（`国家地区`），但只用于**显示** |
| **位置** | `pricing.py:341`、`export_docx.py:274`；参与计算：**无** |
| **差距** | 有数据，无模型 |
| **影响** | 德国货源与上海现货在系统里"等价"，只比单价 |

### 2-11 给 2–3 个可选方案，而不是一个结论

| | |
|---|---|
| **目标** | 「最快」「最便宜」「最稳」三方案，各自成本/交期/风险摆出来，由人决定 |
| **现状** | 只有一条路径：有库存就用库存，否则取最低单价供应商 |
| **位置** | `pricing.py:316-334` |
| **差距** | 是"替你选"，不是"帮你看" |
| **影响** | 无法在成本与交期之间权衡，也无法向客户解释"贵一点但更快"。内部库存优先本身合理，但是个**未声明的隐含假设** |

### 2-12 替代件/等效件

| | |
|---|---|
| **目标** | 客户说"接受同等替代件，请提供差异说明"时，能推荐替代件并生成差异说明 |
| **现状** | 这句话只作为一段文字进 `requirements`，无结构化处理 |
| **位置** | `terms.py:23-31`（7 条英文模式）、`terms.py:151-152`（匹配不上归为"需人工确认"） |
| **差距** | 无替代件知识库、无差异说明生成 |
| **影响** | 一个高价值销售动作（推荐替代、解释差异）完全不被支持 |

> **分析层判定：目前回答的是"这货能不能卖"，不是"这单值不值得做"。** 而且所有商务信息（备注、交期、优先级、国别）**都已经在数据里**，只是**没进决策**——不是数据不够，是模型不够：定价模型里没有"运费项"这个位置，有数据也无处安放。

## 2.3 审核流程与人工知识

### 3-1 阻塞项变成可回答的问题

| | |
|---|---|
| **目标** | 把"这行不行"变成"这行有三个选项，你选哪个、理由是什么" |
| **现状** | **✅ 做得很好。** 复核项 ID 由目标推导、答完不重编号，决策日志可追溯到具体对象 |
| **位置** | `pricing.py:538-659`、`service.py:121-150` |
| **差距** | 无（强项） |

### 3-2 一行有多个问题时可同时处理

| | |
|---|---|
| **目标** | 同一行"MOQ 超量"与"证书不符"应能分别作答：超量可接受、证书不行 |
| **现状** | 一行的答案只能存**一个**。选项列表给了多个，选了其中一个，另一个就再点不了（该项状态变为"已回答"） |
| **位置** | 答案存储 `service.py:228`（`task.resolutions[key] = option_id`，key 是行 ID）；放宽规则 `pricing.py:301-307`（一次只放宽一组） |
| **差距** | 结构上不支持"多约束并存" |
| **影响** | 真实业务里这是两个独立判断。系统把人逼进"只能放宽一条"的死角，或让人放弃报价 |

### 3-3 不确定程度要能表达

| | |
|---|---|
| **目标** | 可信度分档：证据齐全=高；归一化匹配=中；PMA+价格过期=低 |
| **现状** | 只有两个写死标签，且不来自任何计算 |
| **位置** | `pricing.py:398`（`"medium"`）、`pricing.py:443`（`"low"`） |
| **差距** | 无分数、无分级、无"证据完备度"概念 |
| **影响** | "精确匹配+证书齐全+现货+有效期充足"与"归一化匹配+PMA+过期 3 天"，风险差 10 倍，标签一样 |

| **目标** | 有些行结论是"能用但必须注明差异"，既不是"不能报"也不是"能报" |

| **影响** | 大量本可报价的行被卡死；一旦人工放宽，又缺"必须注明"的强制约束 |

### 3-5 人工判断沉淀成知识

| | |
|---|---|
| **目标** | "这家供应商的 8130-3 可靠""这个件号的等效替代是 X""这位客户历来接受 CoC"——应被记住，下次自动带出 |

|---|---|
| **目标** | 这单值不值得报（毛利总额、客户历史、竞争）；有无合规风险（出口管制、最终用户、贸易条款） |

### 4-7 客户明示的三项要求

C/F 邮件正文明确要求：`Unit price, total price, and delivery lead time` / `Validity period` / `Compliance declaration`。

| 客户要求 | 系统状态 | 实际写法 |
|---|---|---|
| 单价 | ⚠️ 给了，但填在「金额」列 | 语义错位 |
| 总价 | ✅ | 行小计 + 总金额 |

# 第三部分　根因

## 根因 1：验收标准定成了"六个案例跑通"

`tests/fixtures/expected/buyer_b.json` 有 **97 KB**，把 B 案例 21 行结果逐字段冻结。工程上这是对的（回归保护），但作为**唯一成功标准**，它会系统性把"泛化能力"换成"对齐能力"。

证据：122 个测试里**没有一条用"没见过的输入格式"**。所以解析器换种表头就崩，而测试全绿。

## 根因 2：模型被定位成"解释器"而非"控制器"

`genesis.py:236-238`：「所有价格、金额、数量、MOQ、交期只能来自工具返回。禁止自己算、自己猜、自己编。」

这条**完全正确**，是最值得保留的判断。但副作用是：为守住"模型不算数"，把模型整体职责一起缩小成了"解释已有结果"。

正确的切分：**算术交给引擎，理解交给模型，两者用契约隔离。**
现在的切分：**算术交给引擎，理解也交给引擎（if-else），模型只剩嘴。**

## 根因 3：缺少"抽取契约"这层中间表示

解析是"字节 → 数据行"一步到位，于是：

- 无法表达"字段抽到了但不确定"（无置信度载体）；
- 无法表达"有个没见过的列"（未识别列直接丢弃，`ingest.py:110-116`）；
- 无法表达"这句是要求还是备注"（只有编号行和 Remarks 块两条规则）；
- 无法"部分成功"（21 行里第 18 行数量写 `N/A`，整封抛错）。

**没有中间表示的抽取系统，只能靠写更多解析器来扩展**——这正是当前演进方向，也是它在第 7 个客户面前必然失效的原因。

## 根因 4：定价模型里没有"成本项"这个位置

`DEFAULT_POLICY` 只有 4 个键（`policy.py:11-22`）。这是"定价参数表"，不是"定价模型"。

没有"运费"这个**位置**，即使数据里有国别（65.5% 跨境）也无处可用；没有"毛利分档"这个位置，`备注：含加急服务费` 无法转化为"这行不加急加价"。

**数据结构决定能力上限。**

# 第六部分　三条不能让步的边界

改造中以下三条一旦被"用 AI 增强"冲掉，项目就废了。

1. **数字只由确定性引擎产出。** 每项成本都必须是可复算的函数。模型只能选"用哪个方案"，不能给"大概 2000 左右"。当前 `pricing.py` 纯函数、无时钟、无网络——**满分，不能动**。
2. **不确定必须显式，不能默认为通过。** 当前证书/件状/单位阻塞逻辑是对的。新增置信度分级**只能让更多东西显式化，不能用来放宽**。特别是：模型自报的 confidence 不能直接当门禁依据，必须配可核验的证据。
3. **对外输出永远是草案，除非具名人类批准。** `service.py:370-401` 的三重拒绝是这套代码最漂亮的一段。新增多语言/多模板渲染后必须原样保留——**渲染层不能有绕过门禁的路径**。

# 第七部分　目标形态（改造后应该长什么样）

> 这一节回答"那到底该做成什么样"，供工程排期使用。核心原则不变：**算术归引擎，理解归模型，两者用契约隔离。**

## 7.1 分层

```text
L4  交互层    对话 / 复核面板 / 方案对比 / 多语言
L3  控制面（模型）  意图识别 · 工具选择 · 抽取 · 提问 · 编排 · 解释
                   ✗ 不产出任何数字
L2  工具层     ingest_* · extract_* · compare_* · price_* · render_*
                   （每个工具都有 JSON Schema，是能力的唯一入口）
L1  事实层     价格表 · 成本表 · 汇率 · 运费表 · 重量表 · 供应商档案
                   客户档案 · 历史成交 · 料号等效关系
L0  证据层     每个数字都能回到 文件→页/表→行→列→原值
```

与现状的差别只有一处，但是决定性的：**L3 的职责从"解释结果"扩展到"理解输入 + 编排动作"，而 L2 从"任务操作"扩展成"既能读原始输入、又能算钱"。**

## 7.2 需要新增的感知类工具

现有 10 个工具全是"任务操作类"，缺"感知类"：

| 工具 | 作用 | 解决哪一条 |
|---|---|---|
| `list_sources(mail_id)` | 列出内容块（正文/HTML/每个附件） | 1-2 附件被忽略 |
| `read_block(block_id, kind)` | 按块读取文本/表格候选 | 1-2、1-4 |
| `classify_document(block_id)` | 判断这是什么文档 | 1-1 |
| `extract_lines(block_id)` | 抽行项目（带锚点与置信度） | 1-3、1-5 |
| `extract_terms(block_id)` | 抽条款（不限编号格式） | 1-7 |
| `resolve_field(line_id, field)` | 低置信度字段的追问出口 | 3-3、3-4 |
| `lookup_master(pn)` | 物料主数据、替代件、历史 | 2-9、2-12 |
| `compare_sourcing(line_id)` | 输出 2–3 个方案 | 2-11 |
| `render_quote(model, locale)` | 多语言多模板渲染 | 4-1、4-3 |

## 7.3 抽取契约（最关键的一个设计）

```json
{
  "line": {
    "part_number": {"value": "MS28775-225", "raw": "MS28775 - 225",
                    "anchor": {"block": "b3", "row": 12, "col": "B"},
                    "confidence": 0.97, "evidence": ["格式符合航空件号规则"]},
    "quantity":    {"value": "8", "raw": "8", "confidence": 0.99},
    "condition":   {"value": ["FN", "NE"], "raw": "FN/NE", "confidence": 0.72,
                    "evidence": ["客户原文为集合写法，已按分隔符切分"],
                    "needs_review": true}
  },
  "unknown_columns": ["客户自定义列 X"],
  "unparsed_rows": [{"row": 18, "reason": "数量为 N/A"}]
}
```

`unknown_columns` / `unparsed_rows` / `needs_review` 三个字段是关键——它们让系统**有能力说出"我没看懂的部分是什么"**。当前系统只有两个状态：成功（拿到行数据）或抛错（信消失）。

有了契约，"不确定怎么处理"才有答案：

| 置信度 | 处理 |
|---|---|
| ≥ 0.95 且校验通过 | 自动采用 |
| 0.7–0.95 或校验有歧义 | 采用 + 进复核（标明"最佳猜测，原文是 X"） |
| < 0.7 或结构性缺失 | 不采用 + 进复核（"这行我看不懂，请手工填"） |
| 未知列 / 未解析行 | 原样展示 + 问"这列什么意思" |

**这套分级，现有系统一个都没有。**

## 7.4 商务引擎：把成本算成 landed cost

需要新增四张表：

| 表 | 关键字段 | 来源 |
|---|---|---|
| 运费表 | 起运国、目的国、重量区间、计费重、时效 | 物流商报价 |
| 物料重量表 | 件号、净重、包装尺寸 | 物料主数据 |
| 毛利策略 | 料号类别、金额档、客户等级、紧急度、目标毛利率、最低加价 | 商务政策 |
| 供应商档案 | 准时率、平均响应、历史退款、清关时效 | 履约历史 |

输出从"一个数"变成"可展开的成本结构"：

```text
landed_cost = 单价×汇率 + 运费(重量,起运国,时效) + 关税增值税 + 包装费(若备注未含) + 加急费(若 AOG 且非现货) - 批量折扣

可承诺交期 = 供应商交期 + 干线运输 + 清关 + 境内配送
可行性     = 可承诺交期 ≤ 客户要求到货日      ← 该字段当前不存在，需新增

报价单价   = landed_cost / (1 - 目标毛利率)   ← 注意不是 cost×(1+markup)
约束       = 报价单价 ≥ landed_cost × (1 + 最低加价)   ← 毛利保护线
```

这组式子同时解决了用户提的三个点：备注（进包装费/加急费/付款条件）、利润（分档毛利）、交期与运费（显式成本项）。

## 7.5 审核与知识沉淀

三级门禁替代当前二值：

| 级别 | 触发 | 交互 |
|---|---|---|
| L0 自动 | 全部规则 pass 且置信度 ≥ 0.95 | 直接进草案，事后可查 |
| L1 建议确认 | 软规则 warn（交期紧、毛利薄、备注冲突） | 给建议 + 理由，一键接受 |
| L2 强制介入 | 硬规则 fail（证书、件号、单位、件状） | 必须选择，不能跳过 |

知识沉淀三条路径（当前全缺）：

1. **决策回写**：人工选 `accept_pma` → 写入"该客户/该料号接受 PMA"的候选知识 → 下次同条件**建议**（不自动采用）。
2. **规则晋升**：同一兜底答案被采纳 N 次 → 提议"变成默认规则" → 人工批准 → 进 `policy_version`。
3. **反例库**：人工驳回某推荐 → 记录反例 → 下次相同上下文降低置信度。

**关键约束**：知识只能改变"建议哪些选项"和"默认选哪个"，**不能改变"是否放行"**。放行永远是人的动作——这样既沉淀知识，又不破坏现有 fail-closed 边界。

## 7.6 产出：内容模型与渲染分离

当前 `export_docx.py` 把"报价内容"和"docx 操作"耦合在一起（316 行里 200 行在操作 `table.rows[i].cells[j]`）。应先产出语言/模板无关的模型：

```text
QuoteModel = {
  meta:   {rfq_no, customer, quote_no, issue_date, valid_until, currency, locale, incoterm},
  lines:  [{no, pn, description, spec, condition, certificate,
            qty, unit, unit_price, line_total, lead_time, moq, ships_from, remarks[]}],
  totals: {subtotal, tax, freight, discount, grand_total, in_words},
  terms:  {payment, warranty, validity, compliance_statement}
}
```

再由 `render_docx(model, template, locale)` / `render_pdf` / `render_xlsx` / `render_email_body` 输出。语言处理放在渲染层：一个 `i18n/{zh,en}.json` 文案字典 + 多语言的大写金额实现。

币种放进 `meta.currency`，`totals` 里每个金额携带币种与汇率快照（"USD 3078.06 × 7.10 = CNY 21,854.23"）——既满足客户核对，也满足审计。

**收益不只是"能做英文"**：拆成"模型 + 渲染器"后，加一个语言、加一个模板、加一个输出格式，成本从"改一处逻辑"降到"加一个文件"。
