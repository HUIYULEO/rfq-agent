# RFQ Agent：业务逻辑与当前实现的证据说明

> 2026-11-02 审阅稿。对象是**收到客户询价、准备向客户报价的供应商**。本文解释现状与拟采用的业务边界，**不批准任何企业价格、交期或合规政策**。本轮只审阅，不把建议视为已实现。

## 1. 先确定哪些话有依据

本文给每项结论标注四种性质：

- **素材事实**：赛事提供的邮件、附件、参考表或报价模板能直接核对。
- **外部参考**：公开产品/监管原始资料支持的通用流程或航空要求；不是本企业政策。
- **现有实现**：以本仓库代码为准，可能只是演示行为。
- **待确认政策**：企业/客户没有给出依据，系统不得冒充行业标准自动决定。

证据优先级按问题分开：客户 RFQ 决定“客户要求了什么”；企业的有效数据与已批准政策决定“能提供什么、报多少钱”；行业资料只帮助确定需要检查的类别，不能替代这两者。赛事素材中没有企业定价授权、毛利底线、税费、库存预留、供应商批准名单或出口管制判断。过去文档中“30 天常见”“FN 最严”“AOG 一小时”等说法均**不得升格为默认业务规则**：即使某公开案例有类似实践，也不证明本企业或该客户适用。

## 2. 整套业务流程：每一步要回答什么

| 步骤 | 业务问题与可执行动作 | 输出/异常去向 | 依据 |
|---|---|---|---|
| 1 接收 | 哪封客户邮件、哪些附件属于同一请求？保存原文、接收时间、文件哈希和关联；明确是否需要回函截止 | 原始资料与任务 ID；无法读取则技术失败 | L1；E1 的询价→报价关系 |
| 2 解析 | 从正文/Excel/PDF 提取客户、RFQ 编号、PN、描述、数量、单位、件状、客户条款；逐字段保留原文和位置 | 结构化 RFQ；读不准的字段待澄清，不猜测 | L1；E1 的抬头/行项目结构 |
| 3 核对客户要求 | 区分**回复截止日**、客户期望**到货日**、拟承诺**交期**；辨别重复行是否真重复、单位是否可比较、证书/追溯/替代要求是否明确 | 问题清单与适用要求，无法消除的关键歧义转 HIL | L1；E1 的有效期/交付结构；航空扩展 E6–E7 |
| 4 冻结可用事实 | 读取内部库存/成本、上游供应商报价、价格状态与日期、MOQ、币种、可售数量；标记数据时间和来源 | 本次事实快照；历史询价看板只供分析，不充当报价 | L1；E3 的主数据/条件 |
| 5 构建候选并验证 | 每个 RFQ 行以**精确 PN**找候选；分别核对身份、单位、数量、件状、证书、价格有效性、MOQ、交付要求等。无证据不能判通过 | 合格、拒绝、待确认及逐项理由；替代件只作人工候选 | L1；E3–E4；航空检查类别 E6–E7 |
| 6 计算方案 | 只对合格且事实充分的候选应用**企业批准的**选源、汇率、费用、税、加价、舍入策略；逐步保存公式与来源 | 可复算的报价建议；无策略或关键金额事实则待决，不填假数字 | E2–E3；企业参数待确认 |
| 7 商业决策与人工介入 | 是否全报、部分报、转上游询价、向客户澄清或不报？对缺事实、例外、授权审批建具名问题和可选动作；人工答复后产生新版本并重算受影响结果 | 明确的商业处置及审批记录，不把“问题已回答”当作“可报价” | E2 的可配置审批；E5 的修订 |
| 8 草案/正式报价 | 草案显示报了哪些行、没报哪些行、价格/币种/数量/有效期/交期/未确认条件；内部批准和对外发送是不同动作 | 与商业处置匹配的文件/询价任务/澄清单；旧版失效 | L1 的模板；E1、E5 |
| 9 结果沉淀 | 保存客户澄清、供应商回价、人工改价、批准、发送、客户反馈、成交/失单原因，并绑定原任务版本 | 可追溯事件与经审核的评测样本；反馈**不自动变成定价规则** | E5 的修订/结果生命周期；产品设计选择 |

这是**目标业务 SOP**，不是声称代码已全部支持。特别是“报价建议”“已批准报价”“已发送客户”“已转订单”应为四个可区分事件。E1/E5 支持这种生命周期分离；当前赛题只要求分析与标准化报价单，正式发送和订单处理没有依据可以自动化。

## 3. 一行询价的判定逻辑

先保存客户原始要求，再判断候选，不应在抽取阶段用当前库存反向改写 RFQ。每项判定保留 `pass / fail / unknown / not_applicable`、证据位置与规则版本：`unknown` 表示**此时不能承诺**，不是 `pass`；`not_applicable` 需要说明为什么不适用。这是拟采用的工程契约，不是 SAP 规定的四值标准。

1. **身份**：PN 精确相同是当前保守入口；别名、替代 PN、航空适装关系需有明确映射/客户接受证据。相同描述不是相同物料。航空场景还需 E6 的适用性/可追溯证据。
2. **量和单位**：需求数量必须为正；内部库存量需与请求单位相同或有批准换算。重复行要逐行保留并累计占用同一库存。上游表若没有数量/UOM，不能从“现货=是”推断足量，也不能悄悄假定每件单价。
3. **件状**：客户明确可接受集合时用集合成员判定；空白是要求不明或未限制，具体行为由客户/企业政策确认。不能硬编码 `FN > NE > OH` 之类的偏序，E6/E7 没有给出这种全局商业替代规则。
4. **证书和追溯**：只有客户/适用法规/企业合同要求时才作为具体资格门；字段“证书类型”不等于已核验证书文件，也不等于安装适用性（E7）。缺证据为 `unknown`，不能由模型生成合规声明。
5. **价格状态/日期/MOQ**：状态有效和日期有效是两个独立检查；状态与日期冲突应保留双方并复核。MOQ 高于需求是采购约束，不代表客户自动接受更大报价数量（E4）。
6. **交付**：回复截止、客户 need-by、供应商 lead time、现货状态各是不同字段。只给“交期天数”没有起算点与物流信息，不能承诺到货日。
7. **金额**：可用成本/供应商价、币种、汇率、报价币种、税费口径、利润规则与舍入顺序都确定后，才生成数值。金额计算应由确定性代码完成，Agent 只负责调工具和解释。

关于部分报价：未报价行明确列出原因，已报价行合计只能称“已报价小计”；是否允许对外发送部分报价是企业/客户政策，不由系统自动默许。无任何有效价格时输出供应商询价任务或客户说明，**不能给空白报价单冒充完成**。

## 4. 参数台账：现值不等于业务依据

下表核对 [`policy.py`](../rfq_agent/policy.py)、[`pricing.py`](../rfq_agent/pricing.py) 和输出代码。标记“演示”的值**只为让样例跑通**；若未提供企业批准配置，生产语义应是“策略未设定，暂停报价”。引用 E2/E3 只能证明“应该由企业配置”，证明不了表中具体数值。

| 参数/行为 | 当前实现 | 依据状态与实际风险 | 目标配置/确认人 |
|---|---|---|---|
| `default_markup_rate` | `0.20`，成本乘 `1.20` | **纯演示假设**；赛事与 E2/E3 未给 20% | 财务/销售批准客户、品类、项目适用的定价规则和最低毛利；缺则停 |
| `cost_basis_priority` | `standard_cost` → `supplier_price`；库存优先 | **演示选源**；并非所有库存均有货权、可售或更优交期 | 运营/财务批准库存可售、成本基线及选源策略 |
| `fx_to_cny` | CNY 1、EUR 7.75、USD 7.1；行内汇率优先 | 固定汇率**纯演示假设**，可能过期；`1` 仅同币种恒等换算 | 财务提供来源、方向、as-of、有效期限；无则停 |
| `rounding_mode`/`price_decimals` | `HALF_UP`、2 位；先换算/舍入成本，再加价/舍入单价 | 技术选择，无企业计价/税费政策依据 | 财务批准每步计算、税费、折扣与舍入规则；保存计算轨迹 |
| `quote_validity_days` | 30 | 仅配置值；现有报价生成逻辑未证明它形成有效的对外承诺 | 销售/法务按客户、货源有效期和报价日确认，不能超过可依赖的上游价格有效期 |
| `allow_split_fulfillment` | `False` | 演示范围限制，暂不自动拼单 | 运营确认是否允许分批、多个来源和分批交期 |
| `allow_moq_overbuy` | `False`；人工选项可 `quote_with_moq` | 默认保守，但人工动作目前会放松 `moq_exceeds`，**不等于客户接受** | 销售/采购分别确认超额采购风险与客户是否接受更大订购量 |
| `allow_expired_price_reference` | `False` | 保守设计；任何例外应有新有效报价或正式授权 | 财务/采购定义过期价能否仅作内部参考，不能自动承诺 |
| 候选排序 | 内部库存第一；供应商中统一成本最低 | 演示策略，没有客户服务、证书、交期、可售量综合依据 | 企业定义先资格后排序、优先级、稳定决胜；不得“最低价即合格” |
| 数量、件状、证书、交期 | 内部库存比数量/件状；供应商缺可售数量仍可给报价建议；证书/交期没有形成统一硬门 | **未充分覆盖业务要求**；参考表字段不等于可验证承诺 | 客户要求和行业/合同适用性确定门禁，缺值待确认 |
| `evaluation_date` | PDF report date 或邮件 Date，也可显式传入 | “邮件日期=实际报价评估日”只是解析回放方便；历史样例的有效性不能直接推到今天 | 每次运行记录实际评估时间；历史回放明确标识为 as-of 演示，不生成当前可发送报价 |
| `auto_draft` | 对 blocking review 自动选择默认选项 | 流程便利设定；可能把待询价/不报价选择记录成“已解决” | 仅用于演示保守任务分流；任何商业例外和正式报价都需具名授权 |

需另建客户/企业政策项：报价币种、价格是否含税、税种税率、运费/包装/关税、Incoterms、付款条款、质保、库存是否预留、供应商准入、报价审批角色与门槛、部分报价许可、客户可接受替代/件状及证书要求。**当前材料没有这些参数的批准值**；输出应写“待确认”或不承诺，不能把假定文案写进正式文件。

## 5. 当前系统到底怎么执行

下面是截至本次审阅的**代码事实**，与 §2 的目标 SOP 分开：

| 模块 | 当前职责/实际行为 | 关键缺口 |
|---|---|---|
| [`ingest.py`](../rfq_agent/ingest.py)、[`sources.py`](../rfq_agent/sources.py)、[`pdf_text.py`](../rfq_agent/pdf_text.py) | EML 正文 HTML/TAB、Excel/PDF 附件解析；规范化为 `RFQ`；保留行号/部分原值 | PDF 解析依赖当前样式；邮件日期常用作评估日期；字段级证据不完整；回复截止与到货日可能混淆 |
| [`models.py`](../rfq_agent/models.py)、[`quality.py`](../rfq_agent/quality.py) | RFQ/Line/Task 数据类、正数数量、重复 PN/混用单位/缺字段/日期提示 | 质量提示未统一成为商业门；`due_at` 被质量模块称为“交期”，源字段实际上是“截止报价日期” |
| [`db.py`](../rfq_agent/db.py)、[`pricing.py`](../rfq_agent/pricing.py) | 两张演示参考表快照、PN 查询；候选状态/日期/MOQ/件状筛选、库存累计分配、Decimal 加价 | 无逐规则四值结果和独立完整性证明；供应商 UOM/可售量缺失但仍报价；证书/交期/客户条款未统一门控 |
| [`terms.py`](../rfq_agent/terms.py) | 英文要求按子串匹配；返回 `met/todo/manual/na`，用于显示/文档 | 不是资格规则；未识别要求只标 `manual`；结果尚不能阻止激活 |
| [`service.py`](../rfq_agent/service.py)、[`storage.py`](../rfq_agent/storage.py) | 创建/分析/报价/复核/导出/激活；revision、持久化 review/interruptions；`activate_quote` 查 `evaluation_status` 和处置 | `_settle()` 用“无 open review”直接标 `complete`，不能证明检查齐全；复核按 line 记一个 resolution 可能覆盖不同规则；`approved_by` 只是输入字符串，无身份/角色验证；导出预览允许非报价处置 |
| [`agent.py`](../rfq_agent/agent.py) | 可选 Deep Agents + Genesis 工具适配，提示模型按工具顺序执行、遇阻塞问人、不可自行算价 | 真实 Web 主路径由 service 直接驱动；工具适配存在不等于每个 RFQ 都由 LLM Agent 自主规划/执行；需以运行 trace 证明 |
| [`ledger.py`](../rfq_agent/ledger.py) | SQLite append-only 事件、任务快照、人工决策、产物和反馈 | 事件可查但还不是字段→事实→规则→算式→产物的完整版本链；反馈不会自动进入评测/规则发布 |
| [`export_docx.py`](../rfq_agent/export_docx.py) | 套用赛事模板动态输出草案和条件摘要 | 条款真实性门禁不足；代码会写“按供应商标准质保”和一段“本报价所涉物项……不含出口管制或限制扩散物项”的**无证据声明**，应在下一次实现中优先移除/改为待签署占位，不得对外使用 |

实际状态路径是 `received → analyzed → awaiting_review / draft_ready → exported → active`，并额外记录 `process_status`、`commercial_disposition`、`evaluation_status`。`start_task()` 是 `create_task → analyze_rfq → build_quote_options`；`analyze_rfq()` 当前主要重新验证 dataclass，不是完整业务分析。人工 `resolve_review()` 修改 resolution、重跑报价、revision 加一；这有持久化雏形，但还不是按具体规则授权的局部恢复。`record_feedback()` 仅追加事件，没有自动学习。所谓 Agent 目前更准确地说是“**可选 LLM 工具入口 + 确定性流程服务**”，核心 Web 路径是否调用模型需按每次 trace 判断，不能因为包名叫 agent 就断言已实现自主 Agent。

## 6. Agent、人和确定性代码的分工

建议用一个任务执行 Agent 作为编排者：接收任务、决定调用哪个已批准工具、读取解析质量和规则结果、发起有证据的人工问题、在答复后恢复、生成解释与任务摘要。它可以从非结构化邮件中**提出**候选字段，但结构化事实必须可追溯并经过校验。Agent 不设金额、不批准例外、不编造证书/可售量/交期、不把历史结果当当前事实。

确定性服务拥有不可绕过的边界：字段验证、规则适用性、候选资格、库存分配、汇率/金额算式、商业处置、产物门禁和版本检查。人负责客户要求歧义、例外授权、供应商询价、政策配置、正式报价批准和对外发送。每个人工动作应带角色、对象、依据和作用范围：例如“接受某行替代件状”不能自动覆盖该候选的过期价格、缺证书或无库存。模型解释应引用服务返回的 rule/evidence ID。

**建议的最小状态约束**：

```text
接收 → 解析 → 校验 → 冻结事实 → 逐项评估
  ├─ 信息/授权不足 → 持久化待办 → 人工答复 → 新 revision → 重评
  └─ 评估完整 → 商业处置 → 对应草案/任务 → 批准 → 可发送版本
技术失败 ≠ 商业上不报价；草案生成 ≠ 已批准；已批准 ≠ 已发送。
```

每个任务至少绑定 RFQ revision、事实快照、策略版本、评估结果和产物 hash；任何影响价格/资格的变化都应使旧产物失效。保留单本 append-only 事件表可以满足赛事规模，不必先造十二套账本；但事件载荷要能回溯每项决定的输入。评测集从 B 的已执行参考案例和 A/C/D/E/F 的**每次新运行**形成，用户修订/反馈先进入待审核样本，不直接“学习”成新策略。真实客户价格与成交结果未提供，当前不能宣称线上优化已经发生。

## 7. 航空扩展的正确位置

通用核心只定义客户要求、物料身份、数量/UOM、候选资格、来源、报价、审批和事件。首个航空扩展可以增加航空 PN/替代件规则、件状词汇、证书类型、适装/追溯/序列号/寿命等字段及证据规则。E6 支持核查质量、适用性、身份与可追溯性；E7 提醒证书不能单独证明适装。**这并不授予系统自动判断可安装、出口合规或所有 `FN`/`NE`/`OH` 之间可替换的能力。** 未拿到客户合同、监管辖区、批准数据和业务责任人签字前，这些只能进入人工复核或“未知”。

## 8. 下阶段实施顺序与先决决策

1. **先止住错误承诺**：修改 DOCX 中无证据的出口管制/质保文字；明确历史样例不能生成当下有效报价；非报价处置不能输出报价单。验收用 B/C 的实际文件检查产物文字与门禁。
2. **补语义与事实边界**：将“截止报价日期”与客户到货要求分开；保留原始字段位置和附件关联；供应商 UOM/可售量缺失应显式显示未知。以 B/C 和一个单位冲突反例验证。
3. **最小规则与 HIL 闭环**：定义关键规则表及 `pass/fail/unknown/not_applicable`，每个 blocking 问题指向具体行/候选/规则；人工动作只改变允许范围；复核后新 revision 重评。无开放问题不再自动等于“评估完整”。
4. **把企业政策与演示策略隔离**：真实运行缺加价、汇率、税费/运费口径、有效期和审批政策时阻塞；演示运行显著标记 demo policy、as-of 日期和不可外发。针对所有数字保存公式/来源。
5. **验证执行 Agent 与数据闭环**：用新提交 RFQ 测试 Agent 工具调用、暂停、恢复、失败；存 trace/反馈；B 仅作可查看的历史参考，其余案例与上传件每次从原文新建任务。将经人工审核的错误加入回归集。

在第 4 步之前需要业务方明确的最小输入：**报价主体和币种、可用/批准的价格来源、成本与加价规则、税费/运费/质保/有效期口径、是否允许部分报价、审批角色、航空件状/证书/追溯要求的适用范围**。没有这些值，系统可以完成询价分析和待办生成，但不能声称生成了可对外使用的正确报价。
