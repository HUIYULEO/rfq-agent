# MatrixNEXT 2026：RFQ 询价分析与报价智能体赛题解析

## 1. 文档目的

本文基于赛事提供的 `询价信息素材` 进行文件级核对，明确赛题的输入、参考数据、预期输出、最小业务闭环和当前证据缺口。本文只描述从素材中能够确认或合理推断的内容；赛事未给出的报价规则不会被写成既定事实。

素材位置：`F:\Codex\MatrixNEXT\询价信息素材`

## 2. 核心结论

该赛题要求构建的不是普通文档问答助手，而是一个能够处理多种客户 RFQ 载体、统一提取行项目、查询内部和外部价格依据、生成报价建议并输出标准报价单的业务智能体。

素材可以分成三层：

1. **客户询价输入**：文件夹 `1` 和 `2` 中的六封 `.eml` 邮件及其附件。
2. **报价参考数据**：价格资源表、内部物料成本表，以及用于历史询价分析的看板演示数据。
3. **报价输出模板**：`报价单样例.docx`。

文件夹 `1` 和 `2` 不是两个客户，而是两组测试批次。每组各包含三位客户、三种不同输入方式，因此一共有六个独立客户请求，可用于验证系统对同一业务在不同载体下的处理能力。

### 3.3 三种标准输入模式

六个客户请求实际覆盖三种输入模式，每种模式有两套样例：

1. **正文型**：询价明细直接位于邮件正文。
2. **Excel 附件型**：正文只说明请求，行项目位于 Excel。
3. **PDF 附件型**：正文包含报价条款，行项目位于 PDF。

因此，第一阶段不需要支持任意文件组合；只要稳定覆盖上述三种模式，即可完成素材范围内的输入闭环。

## 4. 根目录四个文件的角色

### 4.1 `报价单样例.docx`

**角色：最终输出模板。**

模板包含供需双方、联系人、项目名称、报价日期、有效期、产品明细、金额、销售总价、交货时间、税率和备注等区域。智能体最终应填充或生成与其结构等价的标准报价单。

当前模板只有 5 个固定明细行，实际 RFQ 可能超过 5 行，因此最终实现不能简单地只替换现有空格；需要支持动态增加报价行，或生成结构一致的新文档。

### 4.2 `价格资源表_演示数据.xlsx`

**角色：外部供应商价格和履约条件参考。**

共 343 行（含表头）、18 列，主要字段包括：

- Part Number；
- 供应商、供应商类型和国家地区；
- 件状条件；
- 单价、币种和汇率；
- 最小起订量；
- 交期和是否现货；
- 证书类型；
- 报价日期、有效期和价格状态；
- 备注。

该表可用于筛选满足客户数量、件状、证书、有效期和交期要求的候选供应商价格。

### 4.3 `内部物料成本表_演示数据.xlsx`

**角色：内部库存和历史成本依据。**

共 164 行（含表头）、14 列，主要字段包括：

- Part Number 和 Description；
- 产品范围和计量单位；
- 库存数量、仓库和库存件状；
- 标准成本、平均成本和最近采购价；
- 最近采购日期、首选供应商和成本更新日期。

该表可用于判断是否可以从内部库存满足询价，并为成本基线和报价解释提供依据。

### 4.4 `询价报价清单_看板演示数据.xlsx`

**角色：历史询价/运营看板数据，而非直接价格表。**

共 250 行（含表头）、16 列，包含询价单号、询价日期、航空公司、紧急程度、行号、Part Number、数量、产品要求、件状条件和截止日期等字段。

该表没有实际报价金额、毛利或成交结果，因此不能单独用于生成报价。它更适合用于：

- 查看历史询价频率；
- 识别常见物料和紧急程度；
- 作为 RFQ 行项目字段标准化的参考；
- 构建询价看板或展示历史趋势。

## 5. 从素材能够确认的业务闭环

```text
客户 EML
  ├─ 正文中的 RFQ 表格
  ├─ Excel 明细附件
  └─ PDF 明细附件
        ↓
邮件、正文和附件解析
        ↓
统一 RFQ 数据模型
        ↓
字段完整性、重复、冲突与截止日期检查
        ↓
内部库存与成本匹配
        ↓
供应商价格、MOQ、交期、件状、证书和有效期筛选
        ↓
形成候选报价与人工确认项
        ↓
生成标准报价单
```

## 6. 建议的统一 RFQ 数据模型

每个客户请求至少应标准化为：

### 6.1 单据级字段

- 来源邮件文件；
- 客户或发件人；
- 邮件主题；
- RFQ 编号；
- 询价日期；
- 报价截止日期；
- 紧急程度；
- 客户提出的整体报价要求；
- 附件列表。

### 6.2 行项目字段

- 行号或询价单号；
- Part Number；
- Description；
- Quantity；
- Unit Of Measure；
- 优先级；
- 询价产品要求；
- 询价 MPN；
- 件状条件；
- 手册件号；
- 产品范围；
- 行项目截止日期；
- 来源文件和来源位置。

### 6.3 报价候选字段

- 库存可满足数量；
- 内部成本依据；
- 候选供应商；
- 候选采购单价及折算人民币价格；
- MOQ；
- 交期；
- 证书；
- 价格有效期；
- 推荐报价；
- 推荐依据；
- 风险与待人工确认项。

## 7. 赛事没有明确给出的规则

以下内容在现有素材中没有形成明确规则，必须在作品中标记为“方案假设”或“可配置策略”，不能声称来自赛事材料：

- 报价应使用标准成本、平均成本、最近采购价还是供应商价；
- 多个供应商候选的排序权重；
- 利润率或加价率；
- 税率和含税/未税口径；
- 运费、包装费、关税和汇率波动处理；
- 内部库存与外部采购之间的优先级；
- 部分满足和拆单报价规则；
- 过期价格能否作为历史参考；
- 件状条件不一致时是否允许替代；
- 缺少价格时是否转人工询价；
- 最终审批流程。

第一版应采用少量、透明、可调整的确定性规则，并在输出中展示计算依据，不应让大模型自行决定价格。

## 8. 第一版产品边界

### 8.1 必须完成

1. 处理三种输入模式：正文、Excel 附件、PDF 附件。
2. 将六个请求转成统一 RFQ 结构。
3. 识别重复行、缺失字段、单位异常、日期异常和特殊要求。
4. 按 Part Number 查询内部成本和供应商价格。
5. 过滤过期价格及不满足 MOQ、交期、件状或证书要求的候选项。
6. 输出推荐依据及待人工确认项。
7. 生成标准报价单或可下载的报价草案。
8. 保存输入、提取结果、报价依据和输出之间的可追溯关系。

### 8.2 暂不完成

- 汽车模具工程报价；
- 工业图纸多模态分析；
- 任意邮箱自动收信；
- 自动对外发送报价；
- 自动审批；
- 实时外部供应商询价；
- 复杂知识库/RAG；
- 多 Agent 编排；
- 无人工确认的全自动定价。

## 10. MOI 与本地实现的建议分工

考虑到平台导入流程已经出现 HTTP 400，当前不应让项目完全依赖 MOI 的数据导入成功。

建议分工如下：

| 能力 | 首选实现位置 | 说明 |
|---|---|---|
| EML 解析与附件提取 | Windows 本地 | 不假设 MOI 原生支持 EML |
| Excel/PDF 基础解析 | 本地优先，MOI 做兼容性验证 | 保证六个案例可稳定回归 |
| RFQ 统一数据模型 | 本地代码 | 可测试、可版本控制 |
| 报价筛选与计算 | 本地确定性规则 | 避免模型编造价格 |
| 非结构化字段理解 | Genesis | 使用赛事 Credit 和模型能力 |
| 数据表/Workflow | MOI，能稳定运行时使用 | 展示平台结合度，但保留降级路径 |
| 最终交互入口 | MOI Agent 或公开 Web 应用 | 以评委无需安装即可访问为准 |

## 11. 当前风险与待确认项

1. Excel 按官方教程导入时出现 HTTP 400，需记录错误详情并验证是文件、字段、权限还是平台问题。
2. 官方文档没有明确证明 `.eml` 为支持的知识库文件格式。
3. PDF 表格解析质量尚未用赛事样例实际验证。
4. 智能体是否可以公开分享、是否要求评委登录，尚待验证。
5. 工作流是否可以稳定绑定智能体并接受附件，尚待验证。
6. 赛事没有提供明确报价公式，需要自定义透明、可配置的规则。
7. `报价单样例.docx` 固定明细行有限，需要验证动态生成方案。

## 12. 下一步

按以下顺序推进：

1. 本地解析第一组的三封 EML 和两类附件，冻结统一 JSON 输出。
2. 用第二组执行回归验证。
3. 确定最小报价选择规则及人工确认边界。
4. 生成第一份可核对的报价草案。
5. 再决定哪些稳定能力迁移或接入 MOI。
6. 最后创建评委可访问的智能体入口、演示视频和说明文档。

当前最重要的交付目标不是“把所有素材放进 MOI”，而是先证明六类实际请求都能稳定进入同一条可追溯的报价流程。

## 13. 最终提交要求

作品提交时需要提供评委可访问的三个链接，三个字段均为必填：

### 13.1 可运行智能体链接

- 链接必须能够被评委访问；
- 命题赛道需完成真实场景操作；
- 评委应能实际提交或选择 RFQ 样例，查看结构化提取、异常提示、报价依据和报价草案；
- 不应要求评委安装本地软件、配置 API Key 或运行命令；
- 如果必须登录或输入密码，应在说明文档中清楚注明；
- 提交前应使用未登录浏览器或独立账号验证访问权限。

本项目的最低可运行场景应是：

```text
选择一个官方 RFQ 案例
→ 系统识别邮件正文或附件
→ 展示结构化行项目
→ 展示缺失/异常/待确认信息
→ 展示价格依据和建议报价
→ 生成或下载报价草案
```

### 13.2 演示视频链接

- 视频时长不超过 3 分钟；
- 必须说明问题、方案、使用方式和实际效果；
- 视频需要包含真实可运行界面，而不只是架构图或幻灯片；
- 建议完整演示一个官方案例，并快速展示系统支持正文、Excel 和 PDF 三种输入；
- 应录制稳定的固定案例，作为在线智能体临时故障时的可信证据；
- 对报名账号、API Key、访问令牌及个人信息进行打码。

建议视频结构：

1. 20 秒：业务问题与人工流程痛点；
2. 20 秒：方案和数据流；
3. 90 秒：端到端操作演示；
4. 30 秒：报价依据、异常处理和可追溯性；
5. 20 秒：效果、边界及平台能力使用情况。

### 13.3 说明文档链接

说明文档至少包含：

- 问题定义；
- 解决方案；
- 技术栈；
- 创新点；
- 使用说明；
- 命题赛道数据合规说明；
- 智能体和视频的访问方式及密码（如有）；
- 已知限制和人工确认边界。

数据合规说明需要明确：

- 使用赛事提供的演示/脱敏数据；
- 不包含真实客户、供应商、价格或个人敏感信息；
- 用户上传文件的处理范围和保存方式；
- 不使用未经授权的数据训练模型；
- 输出为报价建议或草案，最终价格需人工确认。

### 13.4 提交验收清单

在提交前逐项确认：

- [ ] 三个链接使用未登录浏览器均可访问，或已在说明文档提供访问方式；
- [ ] 智能体可以完成至少一个官方 RFQ 的端到端操作；
- [ ] 视频不超过 3 分钟；
- [ ] 视频内容覆盖问题、方案、使用方式和效果；
- [ ] 说明文档覆盖技术栈、创新点、使用说明和数据合规；
- [ ] 链接中没有暴露 API Key、访问令牌、报名账号或个人信息；
- [ ] 在线服务在评审期间保持运行和足够的 Credit；
- [ ] 已准备固定演示案例和失败时的降级提示；
- [ ] 提交后重新打开页面确认保存成功；
- [ ] 如后续修改链接，重新执行完整访问测试。

最终项目验收标准不是“代码在本地运行”，而是评委通过上述三个链接能够理解问题、操作作品、核对效果并确认数据合规。
