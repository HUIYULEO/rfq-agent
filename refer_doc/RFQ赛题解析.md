# MatrixNEXT 2026：RFQ 询价分析与报价智能体赛题解析

## 1. 文档目的

本文基于赛事提供的 `询价信息素材` 进行文件级核对，明确赛题的输入、参考数据、预期输出、最小业务闭环和当前证据缺口。本文只描述从素材中能够确认或合理推断的内容；赛事未给出的报价规则不会被写成既定事实。

素材位置：`F:\Codex\MatrixNEXT\rfq-agent\data\询价信息素材`（该目录被 `.gitignore` 保护、不入库；上游归档为 `F:\Codex\MatrixNEXT\命题赛道素材.zip`）

## 2. 核心结论

该赛题要求构建的不是普通文档问答助手，而是一个能够处理多种客户 RFQ 载体、统一提取行项目、查询内部和外部价格依据、生成报价建议并输出标准报价单的业务智能体。

素材可以分成三层：

1. **客户询价输入**：文件夹 `1` 和 `2` 中的六封 `.eml` 邮件及其附件。
2. **报价参考数据**：价格资源表、内部物料成本表，以及用于历史询价分析的看板演示数据。
3. **报价输出模板**：`报价单样例.docx`。

文件夹 `1` 和 `2` 不是两个客户，而是两组测试批次。每组各包含三位客户、三个载体类别（正文、Excel 附件、PDF 附件），因此一共有六个独立客户请求，可用于验证系统对同一业务在不同载体下的处理能力。注意“正文型”内部实际有两种不同编码，见 §3.3。

### 3.3 四个输入子型

六个客户请求覆盖三个载体类别；但“正文型”实测有两种不同编码，不能当作同构样例：

| 子型 | 案例 | 实测特征 | 解析难度 |
|---|---|---|---|
| 正文-拼接型 | A | `text/plain` 无分隔符，字段首尾相接（`9000000001PN-0001WASHER 垫片8EA…`） | 高，需锚点切分 |
| 正文-制表符型 | D | `text/plain` 为 TAB 分隔 | 低 |
| Excel 附件型 | B / E | 21 行 × 12 列，均带表头 | 低 |
| PDF 附件型 | C / F | 各 2 页、7 个行项目，`Condition` 列全空 | 中 |

正文型的两个案例都带 `text/html` 部分，其 `<table>` 均为 1 个表、123 个 `<tr>`、1464 个 `<td>`。因此正文型应优先解析 HTML 表格，`text/plain` 仅作降级。

结论：第一阶段不需要支持任意文件组合，但要稳定覆盖上述**四个子型**，且 A 与 D 不能互为等价回归。

## 4. 根目录四个文件的角色

### 4.1 `报价单样例.docx`

**角色：最终输出模板。**

模板包含供需双方、联系人、项目名称、报价日期、报价有效期、产品明细（序号 / 产品名称 / 规格 / 型号 / 数量 / 单位 / 金额 / 销售总价（元）/ 备注）、总金额（大写、小写）、交货时间、质保期和备注等区域。实测模板**没有单价列、没有税率列、没有币种和汇率列**，报价字段的映射见《RFQ_SOLUTION_DESIGN》第 7.5 节。智能体最终应填充或生成与其结构等价的标准报价单。

当前模板只有 5 个固定明细行，实际 RFQ 可能超过 5 行，因此最终实现不能简单地只替换现有空格；需要支持动态增加报价行，或生成结构一致的新文档。

### 4.2 `价格资源表_演示数据.xlsx`

**角色：外部供应商价格和履约条件参考。**

共 343 行（含表头）、18 列，主要字段包括：

- Part Number；
- 供应商、供应商类型和国家地区；
- 件状条件；
- 单价、币种和汇率；
- 最小起订量；
- 交期和是否现货；
- 证书类型；
- 报价日期、有效期和价格状态；
- 备注。

该表可用于筛选满足客户数量、件状、证书、有效期和交期要求的候选供应商价格。

### 4.3 `内部物料成本表_演示数据.xlsx`

**角色：内部库存和历史成本依据。**

共 164 行（含表头）、14 列，主要字段包括：

- Part Number 和 Description；
- 产品范围和计量单位；
- 库存数量、仓库和库存件状；
- 标准成本、平均成本和最近采购价；
- 最近采购日期、首选供应商和成本更新日期。

该表可用于判断是否可以从内部库存满足询价，并为成本基线和报价解释提供依据。

### 4.4 `询价报价清单_看板演示数据.xlsx`

**角色：历史询价/运营看板数据，而非直接价格表。**

共 250 行（含表头）、16 列，包含询价单号、询价日期、航空公司、紧急程度、行号、Part Number、数量、产品要求、件状条件和截止日期等字段。

该表没有实际报价金额、毛利或成交结果，因此不能单独用于生成报价。它更适合用于：

- 查看历史询价频率；
- 识别常见物料和紧急程度；
- 作为 RFQ 行项目字段标准化的参考；
- 构建询价看板或展示历史趋势。

### 4.5 价格覆盖率（已实测）

用 342 行价格资源表与 163 行内部物料成本表核对六个案例。两张表的料号集合完全相同（各 163 个，重合 163），即内部表对“能匹配到哪些料号”没有增量贡献，只贡献库存、成本与件状。

| 案例 | 载体 | 行数 | 料号前缀 | 命中参考表 |
|---|---|---|---|---|
| A | 正文 | 122（108 个不同料号） | `PN-0001`…`PN-0108` | 108 / 108 |
| B | Excel | 21（20 个不同料号） | `PN-0001`…`PN-0020` | 20 / 20 |
| C | PDF | 7 | `GSK-001`…`GSK-007` | 0 / 7 |
| D | 正文 | 122 | `AP-2001`…`AP-2122` | 0 / 122 |
| E | Excel | 21 | `AP-2001`…`AP-2021` | 0 / 21 |
| F | PDF | 7 | `CPL-501`…`CPL-507` | 0 / 7 |

结论：

1. 只有 A、B 两个案例具备验证报价链路的条件；C、D、E、F 全行无价格依据，正确期望结果是逐行 `needs_review`，理由为“无价格依据”。
2. B 要分两层看：供应商层 16 / 21 行有合格候选；叠加内部库存（内部优先策略）后 **19 / 21 行可报价、2 行转人工**（PN-0015、PN-0018：内部件状 NE 不符客户要求的 FN，供应商 MOQ 50/200/500 又大于需求量）。A 的转人工行数须在 P1/P3 冻结黄金值时确定。
3. 163 个料号中只有 108 个被任何 RFQ 引用；`PN-2001`…`PN-2025` 与 30 个真实航空格式料号（如 `MS28775-225`）无人引用。
4. 六个案例使用四套互不相通的料号词表（`PN-####`、`AP-####`、`GSK-###`、`CPL-###`），不能假设跨案例可复用匹配规则或权重。
5. 合格候选口径：价格状态=有效 ∧ 有效期至≥业务日期 ∧ 最小起订量≤数量 ∧ 件状=FN。更换口径会改变 B 的 5 行结果。

## 5. 从素材能够确认的业务闭环

```text
客户 EML
  ├─ 正文中的 RFQ 表格
  ├─ Excel 明细附件
  └─ PDF 明细附件
        ↓
邮件、正文和附件解析
        ↓
统一 RFQ 数据模型
        ↓
字段完整性、重复、冲突与截止日期检查
        ↓
内部库存与成本匹配
        ↓
供应商价格、MOQ、交期、件状、证书和有效期筛选
        ↓
形成候选报价与人工确认项
        ↓
生成标准报价单
```

## 6. 建议的统一 RFQ 数据模型

每个客户请求至少应标准化为：

### 6.1 单据级字段

- 来源邮件文件；
- 客户或发件人；
- 邮件主题；
- RFQ 编号；
- 询价日期；
- 报价截止日期；
- 紧急程度；
- 客户提出的整体报价要求；
- 附件列表。

### 6.2 行项目字段

- 行号或询价单号；
- Part Number；
- Description；
- Quantity；
- Unit Of Measure；
- 优先级；
- 询价产品要求；
- 询价 MPN；
- 件状条件；
- 手册件号；
- 产品范围；
- 行项目截止日期；
- 来源文件和来源位置。

### 6.3 报价候选字段

- 库存可满足数量；
- 内部成本依据；
- 候选供应商；
- 候选采购单价及折算人民币价格；
- MOQ；
- 交期；
- 证书；
- 价格有效期；
- 推荐报价；
- 推荐依据；
- 风险与待人工确认项。

## 7. 赛事没有明确给出的规则

以下内容在现有素材中没有形成明确规则，必须在作品中标记为“方案假设”或“可配置策略”，不能声称来自赛事材料：

- 报价应使用标准成本、平均成本、最近采购价还是供应商价；
- 多个供应商候选的排序权重；
- 利润率或加价率；
- 税率和含税/未税口径；
- 运费、包装费、关税和汇率波动处理；
- 内部库存与外部采购之间的优先级；
- 部分满足和拆单报价规则；
- 过期价格能否作为历史参考；
- 件状条件不一致时是否允许替代；
- 缺少价格时是否转人工询价；
- 最终审批流程。

第一版应采用少量、透明、可调整的确定性规则，并在输出中展示计算依据，不应让大模型自行决定价格。

## 8. 第一版产品边界

### 8.1 必须完成

1. 处理四个输入子型：正文-拼接型、正文-制表符型、Excel 附件、PDF 附件。

## 10. MOI 与本地实现的建议分工

考虑到平台导入流程已经出现 HTTP 400，当前不应让项目完全依赖 MOI 的数据导入成功。

建议分工如下：

| 能力 | 首选实现位置 | 说明 |
|---|---|---|
| EML 解析与附件提取 | Windows 本地 | 不假设 MOI 原生支持 EML |
| Excel/PDF 基础解析 | 本地优先，MOI 做兼容性验证 | 保证六个案例可稳定回归 |
| RFQ 统一数据模型 | 本地代码 | 可测试、可版本控制 |
| 报价筛选与计算 | 本地确定性规则 | 避免模型编造价格 |
| 非结构化字段理解 | Genesis | 使用赛事 Credit 和模型能力 |
| 数据表/Workflow | MOI，能稳定运行时使用 | 展示平台结合度，但保留降级路径 |
| 最终交互入口 | MOI Agent 或公开 Web 应用 | 以评委无需安装即可访问为准 |

## 11. 当前风险与待确认项

1. Excel 按官方教程导入时出现 HTTP 400，需记录错误详情并验证是文件、字段、权限还是平台问题。
2. 官方文档没有明确证明 `.eml` 为支持的知识库文件格式。
3. 两份 `Quote.pdf` 均为 ReportLab 生成、文本流未压缩（各 2 页、7 个行项目，字段可按文本操作符顺序直读），文本层抽取已实测可行；但表格还原库选型（按列坐标重建）尚未验证，且 `Condition` 列全空，件状只能判 `unknown`。
4. 智能体是否可以公开分享、是否要求评委登录，尚待验证。
5. 工作流是否可以稳定绑定智能体并接受附件，尚待验证。
6. 赛事没有提供明确报价公式，需要自定义透明、可配置的规则。
7. `报价单样例.docx` 明细表实测只有 5 个固定行（表体共 9 行：表头 + 5 明细 + 总金额 + 交货时间 + 备注），而 B 需 21 行、C 需 7 行，必须验证动态增行方案。
8. 四个案例（C/D/E/F）完全无价格覆盖，报价链路只能在 A/B 上验证；这不是缺陷，但必须在演示和说明文档中写明，否则会被误判为匹配失败。
9. 价格参考表内有 27 行“价格状态=已过期”但“有效期至”仍在未来（最近为 2026-09-13），两个字段存在语义冲突，必须先定口径再实现过滤。

## 13. 最终提交要求

作品提交时需要提供评委可访问的三个链接，三个字段均为必填：

### 13.1 可运行智能体链接

- 链接必须能够被评委访问；
- 命题赛道需完成真实场景操作；
- 评委应能实际提交或选择 RFQ 样例，查看结构化提取、异常提示、报价依据和报价草案；
- 不应要求评委安装本地软件、配置 API Key 或运行命令；
- 如果必须登录或输入密码，应在说明文档中清楚注明；
- 提交前应使用未登录浏览器或独立账号验证访问权限。

本项目的最低可运行场景应是：

```text
选择一个官方 RFQ 案例
→ 系统识别邮件正文或附件
→ 展示结构化行项目
→ 展示缺失/异常/待确认信息
→ 展示价格依据和建议报价
→ 生成或下载报价草案
```

### 13.2 演示视频链接

- 视频时长不超过 3 分钟；
- 必须说明问题、方案、使用方式和实际效果；
- 视频需要包含真实可运行界面，而不只是架构图或幻灯片；
- 建议完整演示一个官方案例，并快速展示系统支持正文、Excel 和 PDF 三种输入；
- 应录制稳定的固定案例，作为在线智能体临时故障时的可信证据；
- 对报名账号、API Key、访问令牌及个人信息进行打码。

建议视频结构：

1. 20 秒：业务问题与人工流程痛点；
2. 20 秒：方案和数据流；
3. 90 秒：端到端操作演示；
4. 30 秒：报价依据、异常处理和可追溯性；
5. 20 秒：效果、边界及平台能力使用情况。

### 13.3 说明文档链接

说明文档至少包含：

- 问题定义；
- 解决方案；
- 技术栈；
- 创新点；
- 使用说明；
- 命题赛道数据合规说明；
- 智能体和视频的访问方式及密码（如有）；
- 已知限制和人工确认边界。

数据合规说明需要明确：

- 使用赛事提供的演示/脱敏数据；
- 不包含真实客户、供应商、价格或个人敏感信息；
- 用户上传文件的处理范围和保存方式；
- 不使用未经授权的数据训练模型；
- 输出为报价建议或草案，最终价格需人工确认。

### 13.4 提交验收清单

在提交前逐项确认：

- [ ] 三个链接使用未登录浏览器均可访问，或已在说明文档提供访问方式；
- [ ] 智能体可以完成至少一个官方 RFQ 的端到端操作；
- [ ] 视频不超过 3 分钟；
- [ ] 视频内容覆盖问题、方案、使用方式和效果；
- [ ] 说明文档覆盖技术栈、创新点、使用说明和数据合规；
- [ ] 链接中没有暴露 API Key、访问令牌、报名账号或个人信息；
- [ ] 在线服务在评审期间保持运行和足够的 Credit；
- [ ] 已准备固定演示案例和失败时的降级提示；
- [ ] 提交后重新打开页面确认保存成功；
- [ ] 如后续修改链接，重新执行完整访问测试。

最终项目验收标准不是“代码在本地运行”，而是评委通过上述三个链接能够理解问题、操作作品、核对效果并确认数据合规。
