# V2 需求与赛题边界的对照审查

> 日期：2026-11-02
> 审查对象：[RFQ_AGENT_V2_DEVELOPMENT_REQUIREMENTS.md](./RFQ_AGENT_V2_DEVELOPMENT_REQUIREMENTS.md)（541 行，12 P0 + 7 P1 + 5 P2 + 26 验收场景）
> 对照基准：赛题 §8 第一版产品边界、[RFQ_BASELINE_DESIGN.md](./RFQ_BASELINE_DESIGN.md)（Baseline v1.0）、现有代码与实测数据

## 0. 结论

1. **业务契约没跑偏。** V2 的每一条硬约束都能对回赛题 §8.1 的八项要求，方向是"更严"，不是"另起一套"。
2. **交付形态跑偏了。** 它把自建基准的第二次泛化当成本次比赛的开发计划：12 项 P0 要求"全部实现 + 26 场景自动化 + eval 报告"，这是内部平台 v2.0 的验收标准，按它推进，比赛交付（链接、视频、一页说明）会被无限推后。
3. **有约 5 条值得照做，其余是冗余。** 其中"单位不一致仍照常报价"是结构缺口（候选构造时单位就丢了），但现有数据自洽、尚未触发；而三层知识、eval 闭环、计划编译器、12 本账本，对 6 个案例、21 行的规模属于过度设计，且与赛题 §8.2 明确排除的范围直接冲突。

### 3.2 内部重复（落地时会产生三套代码）

- **同一条禁令写三遍**：`evaluation_status=incomplete` 不得进入 `settled`/`artifact_ready`，出现在 §5.2（L152）、§6.3（L243）、§14 完成定义（L533）。
- **验收清单三套且编号不对应**：§9 基准矩阵 17 条、§13 场景 AC-01…AC-26、§11.2 指标 10 条。同一个"计划完整性"在 §6.2、AC-12、§11.2 各有一套表述，实现时无法一一对号。
- **12 本账本大量重叠**（§10）：Fact Ledger 记的候选事实 = §5.1 的 `candidate_set_id`；Evaluation Ledger 记的计划 = `evaluation_plan_id`；Pricing Ledger 记的步骤 = §8.3 的计算轨迹。三本账实际是同一份数据写三张表。现有 `ledger.py` 用**一张** `operational_event` 表就覆盖了 agent trace / artifact / human decision，是更务实的选择。
- **两套状态机并存**：V2 §5.2 的 `process_status` 是八态（received→parsed→validated→evaluated→awaiting_review→settled→artifact_ready→completed），代码里实际在跑六态（received / analyzed / awaiting_review / draft_ready / exported / active）。迁移不改任何业务结果，但要动 UI 文案、测试断言和演示脚本。

### 3.3 规模不匹配（成本远大于收益）

| V2 要求 | 现状 | 评估 |
|---|---|---|
| §6 EvaluationPlan：稳定 key + 字节级 hash + 计划/结果双完整性校验 | 规则是 `pricing.py` 里十来个 `if`（件状/证书/MOQ/有效期/状态/数量/库存/单位） | 工作量约为定价引擎的 2–3 倍；它防的是"漏了一条规则"，用"规则清单 + 每条规则一个反例测试"能覆盖大部分 |
| §7.2 恢复流程 8 步：依赖图、按 hash 复用、从最早受影响阶段重启 | 单进程、单用户、3 分钟演示 | 分布式工作流引擎的能力，当前无对应用例 |
| §10 十二本账本 | 一张事件表 + 任务快照 | 存储与查询成本翻十倍，回放价值可用快照 API 达到 |

## 5. V2 指出的 UOM 缺口：结构上存在，当前未触发

`pricing.py` 从不比较候选的 `Unit Of Measure` 与行项目的 `unit`，只有一行回显：`"unit": line.unit`（L323）。构造候选时**单位字段根本没有进入候选字典**（`supplier_candidates` / `internal_candidates` 的键里都没有单位），所以不是"比较漏了"，而是"信息在被比较之前就丢了"。

但实测**没有发生错价**，这一点要说明白：

| 事实 | 数据 |
|---|---|
| A/B 里 5 个 `IN` 料号（PN-0017/0051/0068/0085/0102） | 成本表里它们的库存单位**也是 IN**，行单位与库存一致 |
| D 的 7 行、E 的 1 行 `FT` 料号（AP-2017…AP-2119） | 成本表里**没有这些料号**，D/E 全部 0 候选，走不到定价 |
| 价格资源表 | **没有单位列**，供应商报价在源头就不带单位，无法比较，只能按"未声明"处理 |

所以这是**潜在缺陷（latent），不是正在发生的错误**：现有数据自洽，一次也没被触发。价值在于"以后加一个 FT 库存行就会静默错价"，不在于"现在算错了钱"。

V2 的 AC-08 方向正确（单位不一致 → `unknown`，禁止报价），但按它的严格程度执行，供应商报价会因"未声明单位"全部变 `unknown`，A/B 的 109 + 19 行报价会直接归零——比缺陷本身更糟。可执行的版本是：**内部库存比单位，供应商按"未声明"标注并在依据里写明**。

## 6. 建议的取舍

### 6.1 立刻做（P0'，5 条，全部落在现有代码路径上）

| # | 事项 | 对应 V2 | 为什么现在做 |
|---|---|---|---|
| 1 | 内部库存单位 ≠ 行单位且无换算 → `unknown`，禁止报价；供应商报价无单位时标注"未声明" | AC-08（收窄执行） | 潜在缺陷：现有数据自洽未触发，加一条 FT 库存行就会静默错价 |
| 2 | 四值规则结果（pass / fail / unknown / not_applicable）替代 `eligibility` + 零散 reasons | P0-003 | 用户可见的"依据"升级，也是赛题 §8.1.6 的正解 |
| 3 | 处置与产物门禁：询价 / 无法报价 / 待澄清不得出报价单 | §5.3 | 会误发，属于合规风险 |
| 4 | 最小 ArtifactManifest：产物 ↔ revision ↔ 快照 ↔ 策略版本 + hash，下载时校验 | P0-009 | 比 12 本账本便宜两个数量级，效果相同 |
| 5 | 未注册 / 未知 requirement 保留为 blocking unknown | AC-11 | 接住刚做的 terms 核对，避免"没认出来就丢掉" |

### 6.2 明确降级（写进 backlog，不做）

三层知识/RAG、eval 闭环与硬指标、EvaluationPlan 计划编译器、12 本账本（用 1 本事件表 + 快照 API 代替）、8 步恢复流程、多币种以外的费用口径（税费/运费口径目前明说不计）。

### 6.3 文档先做一次合并

三套验收清单合并为一份（以 AC-01…AC-26 为主线，§9 与 §11.2 只保留未被覆盖的条目），否则实现时无法对号，也无法证明"哪一条过了"。

## 7. 与最初设定的三处张力

| 张力 | 赛题/最初设定 | V2 | 取舍 |
|---|---|---|---|
| 交付形态 | 能跑的链接 + 3 分钟视频 + 一页说明（§13） | P0 全实现 + 26 场景自动化 + eval 报告（§14） | 以交付形态为准，V2 作为内部质量基准 |
| 用户可见性 | 人要能操作、能看见工作流 | 收益几乎全在"不出错"，不产生新的可见能力 | 先做 2（四值依据）和 3（门禁），其余不占演示时间 |
| 可维护性 | 1 名开发者 + 1 个 agent | 规则目录 + 计划编译器 + 12 账本 + 三层知识 + eval，任一处改动都要跑整套 conformance | 超过当前体量，不做 |

## 8. 一句话总结

V2 是一份**合格的产品基准**，但不是**这次的开发计划**：它的业务判断值得照做（尤其是四值结果、产物门禁、可追溯，以及收窄执行后的 UOM 校验），它的工程规模应该砍掉八成。
