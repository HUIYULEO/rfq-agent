## 第一部分：skill 到底是一种什么设计

先把它从"汽车模具"里剥出来。朋友那套东西之所以有效，不是因为公式准，而是因为它**把一类知识安排到了正确的位置**。八条原则，每条都对应一个结构性问题的解法。

### S1. Skill 是"给 Agent 的操作手册"，不是"给 Agent 的功能"

我们现在的思路是给 Agent 加工具（`analyze_rfq`、`build_quote_options`…）。朋友那套的思路是给 Agent 加**判断依据**。

区别在于：工具回答"我能做什么"，手册回答"**什么时候该做、做之前必须先看什么、做完怎么知道对不对**"。他整套的价值八成在 `SKILL.md` 的文字里，不在脚本里——脚本只有 6 个，但 SKILL.md 把"必须先看渲染图再定价"这种顺序强制写成了流程。

**结构性问题的解法**：工具的契约是稳定的，判断力是易失的。把判断力写成可装载、可版本化的文件，它才不会随每次对话漂移。

### S2. 四层分离：决策 / 知识 / 执行 / 契约

```
决策层  SKILL.md          何时用、按什么顺序做、什么时候不要做
知识层  references/*.md   公式、陷阱、反面教材、校准样本（人类可读、可 diff、可反驳）
执行层  scripts/*.py      确定性换算，无业务判断，CLI 可单独跑
契约层  assets/*.json     带 _字段说明 的模板，人机双方唯一的对齐依据
```

**为什么必须分**：混在一起的直接后果是——改一条定价公式要改 Python，改 Python 要重跑全量测试，于是没人敢改，知识就此冻结。分开之后，公式变了只 diff 一个 md，人 review 一次就能批准。

**判据（可直接当 code review 规则用）**：
- 执行层里出现 `if 客户是航空客户` → 错，这是决策层/规则层的事；
- 知识层里出现"调 `calculate_quote()` 拿结果" → 错，这是决策层的事；
- 契约层缺字段说明 → 错，模板就等于没写。

### S3. `description` 是路由器，不是简介

`SKILL.md` 的 frontmatter 决定 **Agent 装不装载这个 skill**。所以它必须一口气说完四件事：触发条件（用户会怎么说话）、输入清单、一句话流程、**已知边界**。

我们的扩展包 manifest 目前只有结构化声明（`extension_id`、兼容版本、operator 列表），没有"什么时候该装载我"。这正是 Agent 选错扩展包、或者装了不用时无法自查的根因。

### S4. "不要硬算"是负向能力，和正向能力同等重要

他的 SKILL.md 有一句：

> 已知边界：模具尺寸公式只覆盖 Progressive / Transfer；其他类型（Tandem/Fine Blanking/Hot Forming）遇到时提示用户，不要硬算。

这一行省下的错误比任何一个公式都多。

我们在**工程层**已经做对了：`unknown` 一律 `needs_review`，不允许静默通过（RULE-007 / baseline §3.4）。我们缺的是**提示词层的 fail-closed**——Agent 该在什么时候停下来说"这个我不确定，需要人"，而不是猜一个值把流程走完。

对应到需求：不是再加一条规则，而是给每个扩展包声明 `unsupported_when`，并由 `analyze_rfq` 在校验阶段把它变成显式的 review item。

### S5. 文件即接口：跳与跳之间用产物，不用函数调用

他的两步之间唯一的耦合是 Gate0 格式的 Excel。好处是人可以中途接手、可以手改、可以重跑、可以换人做。

我们的 `runtime/<task_id>/draft-r<rev>.json` 已经是这个形态，方向一致。**缺的是"可手改"**：目前 JSON 是产物，不是可回灌的输入。人改了没有入口让它生效，只能改代码或改源数据。

### S6. 每个值要自证"可信等级"，不只标"位置"

他的 `estimation.json` 每个字段是 `{value, source}`，`source ∈ {html, computed, press, default}`，其中 `default` 必带 ⚠。

我们的 `evidence: {file, container, row}` 回答"**在哪**"；`source` 回答"**可不可信、是抄的还是算的**"。这两个是正交的两维，我们现在只有一维。

**关键收益**：`default` 级的数字可以被区别对待。一个从兜底表猜出来的开料尺寸和一个从客户图纸读出来的，不该用同一个加价率、也不该有同样的自动通过权。

### S7. 负样本知识是最贵资产，且必须结构化到"动作"

他的陷阱表是四列：**现象 / 误判 / 真相 / 动作**。第四列是关键——没有"动作"的知识等于没写。

而且反面教材是显式的：`Transfer 禁止用 pitch × 工位数算长度（BU 伪公式，实测偏短 50%+）`。"某个维度上公式根本不存在"这个结论，比任何公式都省钱。

我们现在的坑散在 `RFQ_PUSH_REVIEW_2026-11-03.md`、`RFQ_DESIGN_REVIEW.md`、`RFQ_PR1_REVIEW_2026-11-03.md`、`RFQ_V2_REVIEW.md` 四份文档里，还有一部分在测试注释里。**问题不是记录缺失，是这些知识无法被 Agent 读取、无法被回归测试引用、无法在评审时一次讲清。**

### S8. 标定飞轮：常数从样本算，不从代码改

他的规则很克制：样本 <3 家只记录观察值，≥3 家取中位数才更新基准。

但**飞轮没接到引擎上**：文档写着"Transfer 吨价 35k 偏低，待上调至 ~42k"，代码里还是 `35000`。因为常数内联在 `generate_offer.py` 里，改常数等于改代码，没人愿意改。

我们正好相反：常数在 `policy.py` 的 `DEFAULT_POLICY` 里，`POLICY_VERSION = "demo-2026-11-01"` 是一个**手写字符串**。它会被印在报价单上（方案 §14 要求"与 policy_version 一起显示"），但字符串和内容没有任何绑定关系——改了加价率忘了改版本号，报价单就在撒谎。

**正确的形态**：常数外置成数据文件，`policy_version` 由**内容哈希**派生。改一个数字，版本自动变，报价单自动标新版本。

## 第三部分：复用主张

### 核心判断

> **Skill pack 不是新运行时，而是「行业扩展包的第三张脸」。**

baseline §8 已经把扩展包定义成六个代码钩子（`schema_extensions` / `normalizers` / `rules` / `terminology` / `evidence_requirements` / `fixtures`）。这套接口是给**代码**用的。

但 §8 的承诺是"**新增行业只需扩展包，不需修改通用核心**"。要兑现这句话，光有代码钩子不够——还需要回答"**谁来写这个包**"。答案是：一个读得懂自然语言的 Agent（或人），它需要一个 LLM 可读的入口。

于是同一个扩展包有三张脸，服务三个读者：

```
                    ┌─────────────────────────────┐
                    │  扩展包（一个目录，一次版本） │
                    └───────┬─────────┬───────────┘
             ┌──────────────┘         └────────────┐
             ↓                                     ↓
   ┌──────────────────┐                  ┌──────────────────┐
   │ ① 代码脸（已有）  │                  │ ② 手册脸（新增）  │
   │ manifest + rules │                  │ SKILL.md         │
   │ normalizers      │                  │ references/*.md  │
   │ 给引擎读          │                  │ 给 Agent / 人读   │
   └──────────────────┘                  └──────────────────┘
             └──────────────┬────────────────────┘
                            ↓
                 ┌──────────────────────┐
                 │ ③ 常数脸（新增）      │
                 │ calibration.json     │
                 │ 版本 = 内容哈希       │
                 └──────────────────────┘
```

**明确不做的事**（避免和我们自己的 V2 审查结论打架）：
- 不做 skill 装载器 / 不改 Agent 运行时 / 不加子智能体；
- 不让 skill 参与计算；
- 不让 skill 决定 disposition。

Skill 只做两件事：**让 Agent 知道该怎么判断**、**让评审看懂我们凭什么这样判断**。

## 第四部分：七件套规范

一个行业包 = 一个目录，七件。前三件已有，后四件是新增。

```text
extensions/aviation/                    ← 第一个包（航空），现为散落在核心的语义
├── manifest.json          ① 已设计   扩展包声明：id/版本/兼容 core 版本/operator/证据要求
├── normalizers.py         ① 已有     原始字段 → requirement/attribute
├── rules/                 ① 已有     行业资格规则（件状、证书、追溯）
├── SKILL.md               ② 新增     ★ 决策层：触发条件 / 输入清单 / 流程 / 已知边界 / 卡点
├── references/
│   ├── glossary.md        ③ 新增     术语与展示名（EASA Form 1 / PMA / NE / FN…）
│   ├── traps.md           ③ 新增     ★ 反例库：现象 / 误判 / 真相 / 动作
│   └── calibration.md     ③ 新增     常数来源与标定样本说明（人类可读）
├── calibration.json       ④ 新增     ★ 常数：加价率/汇率/费用口径/排序权重
├── schema/                ① 已有     requirement 的 JSON 类型与 operator
└── fixtures/              ① 已有     正反例 + 黄金结果
```

**包里不放 CLI。** 入口永远是核心那一个 `rfq_agent.cli`（它已经能在无 agent、无 Web 的情况下跑完整个案例），包只通过 `manifest.json` 注册自己，由核心按名装载：

```bash
python -m rfq_agent.cli case --case B --pack aviation --export
```

这一条很重要：**包是可被装载的配置，不是可执行的程序。** 如果每个包自带 CLI，就等于给每条业务线开了一个分叉入口，回归时你永远不知道刚才跑的是哪条路径。

### 每件的判定标准（可直接当验收）

| # | 件 | 合格判据 | 不合格的样子 |
|---|---|---|---|
| ① | manifest + normalizers + rules | 核心不含任何航空枚举；未注册 key 保留并转人工 | `compliance.py` 里写着 `"EASA Form 1"` |
| ② | `SKILL.md` | 读完能**不看我方任何其他文档**跑通一个案例；含 `unsupported_when` | 只罗列文件清单，没流程没边界 |
| ③ | `traps.md` | ≥8 条，每条四列，每条带案例编号，每条"动作"可执行 | "注意单位"（没有动作=没写） |
| ④ | `calibration.json` | 常数全部外置；`policy_version` 由哈希派生；改一个数版本自动变 | 版本号手写 `"demo-2026-11-01"` |
| ⑤ | 可被核心 CLI 装载 | `--pack <name>` 生效；不传该参数时行为与今天完全一致 | 包里自带 `main()`；或只能通过 Web 点按钮 |

### `traps.md` 的模板（第四列最重要）

```markdown
| # | 现象 | 常见误判 | 真相 | 动作 |
|---|---|---|---|---|
| T-01 | 案例 D 正文表格 EA/FT 混用 | 按 EA 统一计价 | 单位是原文写死的，不可换算 | 该行进 review（uom_mismatch），不换算、不合并 |
| T-02 | 案例 C 7 行全无价格 | 解析失败 | 料号 GSK-* 在两张参考表零命中 | 任务级一个问题"整体转人工"，不弹 7 个对话框 |
```

判据很简单：**把"动作"列单独抽出来，能不能直接写成一条测试用例。** 能，就是好条目。

## 第六部分：对三份正式文档的最小改动

不重写，只加锚点。

### baseline `RFQ_BASELINE_DESIGN.md`

- **§7 知识与配置基线**：三类资产 → 四类，补一行

  | 资产 | 示例 | 权威用途 |
  |---|---|---|
  | **标定常数**（新增） | 加价率、汇率表、费用口径、排序权重 | 确定性计算，版本由内容哈希派生 |

  理由：现在常数被归进"业务事实数据"或散在代码里，导致"改加价率"既不进事实快照、也不进规则目录，`policy_version` 无从校验。

- **§8 行业扩展包**：六钩子 → 七件套，补三条：`agent_guide`（SKILL.md 决策层）、`traps`（反例库）、`calibration`（常数）。并补一句：

  > 扩展包必须能被**独立装载并执行**（由核心 CLI 以 `--pack` 选择，不依赖 Agent、平台或 Web 层），且不得自带独立入口；否则"新增行业只需扩展包"无法被验证，也无法用一个入口对比两个包的行为差异。

- **§9 验收矩阵**：补两条
  - 18. 扩展包缺少七件套中任一件时，装载失败并报错，不静默降级；
  - 19. 任一标定常数变化时 `policy_version` 随之变化，且报价单上记录的版本可复算出同等哈希。

### solution `RFQ_SOLUTION_DESIGN.md`

- **§9.2 第一版工具**：末尾补一段边界声明

  > 扩展包不注册新工具。Agent 的五个业务工具保持不变；扩展包只改变**规则的输入**（requirement 类型、operator、证据要求）和**Agent 的判断依据**（装载哪份 SKILL.md）。计算路径不因装载了什么包而改变。

## 第七部分：优先级与取舍（关键）

比赛时间有限，六案例里只有 A/B 能验证报价链路。**不是所有 P0 都该现在做。**

### 建议：先做 3 条纯文档，代码改动的延后

| 做什么 | 为什么现在做 | 工作量（估） | 风险 |
|---|---|---|---|
| **EXT-001 七件套骨架** | 定义完规范，后面每条才有落点；纯新增目录 + manifest 校验 | 半天 | 无 |
| **EXT-005 反例库** | 纯文档；立刻能用在答辩（"我们踩过这些坑"）；可回流成回归测试 | 半天 | 无 |
| **EXT-004 SKILL.md 决策层** | 纯文档；把散在四份 review 里的判断力收成一处 | 半天 | 无 |

**延后（P1）**：EXT-002 + EXT-003 必须**成对做**——`--pack` 只有在航空语义已经迁出核心之后才有意义，否则只有一个隐式的"写死的包"，换包无从验证。EXT-006 单独延后（动 `policy.py` 会影响所有金额测试）。

### 为什么这么切

三条先做的**全是加文件、不改业务代码**，因此不影响 M3 六案例验收、不引入回归风险，但能一次性兑现 baseline §8 那句悬着的承诺。

而 EXT-002（航空语义迁出）+ EXT-003（`--pack`）虽然最关键，却是唯一会动到已验证链路的，**必须放在六案例全绿之后**，且前置条件是先用测试把六案例的现有输出逐字节锁住。

### 演示价值最大的那一条

**EXT-002 + EXT-003 + EXT-011 组合**：演示时不说"我们支持多行业"（空话），而是跑同一条入口、换一个参数——

```bash
python -m rfq_agent.cli case --case B --pack aviation --export     # 出报价草案
python -m rfq_agent.cli case --case B --pack electronics --validate # 同一核心、同一入口、另一个包
```

第二个包只做校验、不接业务、不进验收。成本极低，但它是"**同一入口、同一状态机、规则全不同**"最直观的证据——比两次跑不同脚本有力得多，因为评委看的是"核心没变"。

注意：这条依赖 EXT-002 先完成，属于 P1，**不适合当成现在就要交的东西**。

## 一句话结论

**他的 skill 解决的是"知识怎么组织"，我们的 baseline 解决的是"结论怎么保证"。**

这两件事不冲突，且我们缺的正好是前者。所以复用的方式是：

> 给行业扩展包补三张脸——**决策层（SKILL.md）让判断力可装载**、**反例库（traps.md）让经验可测试**、**常数层（calibration.json）让定价可审计**——而不是引入 skill 运行时。

最小可交付：**四份新增文档（manifest 校验 + SKILL.md + traps.md + calibration 说明），不动任何业务代码、不加任何新入口。**
